Persona Use Cases im Cockburn-Format (fully dressed), auf User-Goal-Ebene. Jeder Use Case nennt
die geprüften Geschäftsregeln (BR-IDs, siehe link:spec.adoc[`spec.adoc`]) und schließt mit
EARS-formulierten Einzelanforderungen ab, die 1:1 aus den Extensions abgeleitet sind.

== UC-01: Gegenstand ausgeben

Primary Actor:: Thekendienst
Scope:: System Leihgut
Level:: User Goal
Stakeholder und Interessen::
* Thekendienst: will in Sekunden wissen, ob die Ausgabe zulässig ist.
* Mitglied: will den gewünschten Gegenstand mitnehmen.
* Verein: will keine Ausgabe entgegen Sperre, Wartungsfälligkeit oder fehlender Einweisung.
Precondition:: Der Gegenstand ist im Katalog erfasst.
Trigger:: Ein Mitglied möchte an der Theke einen Gegenstand ausleihen.

Main Success Scenario::
. Thekendienst wählt Gegenstand und Mitglied.
. System prüft: Gegenstand verfügbar oder für dieses Mitglied reserviert (BR-AUS-01).
. System prüft: Mitglied nicht gesperrt (BR-AUS-03).
. System prüft: Mitglied führt weniger als drei Ausleihen (BR-AUS-02).
. System prüft: bei Einweisungspflicht liegt eine gültige Einweisung des Mitglieds für die Kategorie vor (BR-AUS-04).
. System hinterlegt die Kaution nach BR-KAT-04 und setzt die Rückgabefrist auf Ausgabedatum plus Leihdauer der Kategorie (BR-AUS-05).
. System gibt Ausleihe mit Rückgabefrist und hinterlegter Kaution aus.
. Thekendienst übergibt den Gegenstand.

Extensions::
2a. Gegenstand weder verfügbar noch für dieses Mitglied reserviert:::
2a1. System weist die Ausgabe ab. Use Case endet ohne Erfolg.
3a. Mitglied gesperrt:::
3a1. System weist die Ausgabe ab mit Hinweis auf die überfällige Ausleihe. Use Case endet ohne Erfolg.
4a. Mitglied führt bereits drei Ausleihen:::
4a1. System weist die Ausgabe ab. Use Case endet ohne Erfolg.
5a. Gegenstand einweisungspflichtig, keine gültige Einweisung:::
5a1. System weist die Ausgabe ab mit Hinweis auf die fehlende Einweisung. Use Case endet ohne Erfolg.

Postconditions (Erfolg):: Ausleihe ist aktiv, Kaution ist hinterlegt (BR-KAU-04), Rückgabefrist ist gesetzt, Gegenstand ist nicht mehr verfügbar für andere.

.Activity-Diagramm UC-01
[plantuml, uc-01-gegenstand-ausgeben, svg]
----
start
:Gegenstand und Mitglied wählen;
if (Gegenstand verfügbar oder für Mitglied reserviert? [BR-AUS-01]) then (nein)
  :Ausgabe abweisen;
  stop
endif
if (Mitglied gesperrt? [BR-AUS-03]) then (ja)
  :Ausgabe abweisen (Sperre);
  stop
endif
if (Mitglied hat 3 aktive Ausleihen? [BR-AUS-02]) then (ja)
  :Ausgabe abweisen (Limit erreicht);
  stop
endif
if (einweisungspflichtig und keine gültige Einweisung? [BR-AUS-04]) then (ja)
  :Ausgabe abweisen (fehlende Einweisung);
  stop
endif
:Kaution hinterlegen [BR-AUS-05, BR-KAT-04];
:Rückgabefrist setzen [BR-AUS-05];
:Ausleihe anlegen;
:Gegenstand übergeben;
stop
----

EARS-Anforderungen::
* REQ-UC01-01: Wenn ein Gegenstand ausgegeben werden soll, der weder verfügbar noch für das anfragende Mitglied reserviert ist, shall das System die Ausgabe ablehnen.
* REQ-UC01-02: Wenn ein gesperrtes Mitglied eine Ausgabe anfragt, shall das System die Ausgabe ablehnen.
* REQ-UC01-03: Wenn ein Mitglied bereits drei aktive Ausleihen führt, shall das System eine weitere Ausgabe an dieses Mitglied ablehnen.
* REQ-UC01-04: Wenn ein einweisungspflichtiger Gegenstand ohne gültige, nicht widerrufene Einweisung des Mitglieds für die Kategorie ausgegeben werden soll, shall das System die Ausgabe ablehnen.
* REQ-UC01-05: Wenn eine Ausgabe zulässig ist, shall das System die Kaution nach BR-KAT-04 hinterlegen und die Rückgabefrist auf Ausgabedatum plus Leihdauer der Kategorie setzen.

== UC-02: Ausleihe verlängern

Primary Actor:: Thekendienst
Scope:: System Leihgut
Level:: User Goal
Precondition:: Die Ausleihe ist aktiv.
Trigger:: Ein Mitglied möchte eine laufende Ausleihe verlängern.

Main Success Scenario::
. Thekendienst wählt die Ausleihe.
. System prüft: Ausleihe nicht überfällig (BR-AUS-07).
. System prüft: keine offene Vormerkung für die Kategorie des Gegenstands (BR-AUS-07).
. System prüft: Mitglied nicht gesperrt (BR-AUS-08).
. System prüft: Ausleihe noch nicht verlängert (BR-AUS-06).
. System verlängert die Rückgabefrist um die volle Leihdauer der Kategorie; die hinterlegte Kaution bleibt unverändert (BR-AUS-09).

Extensions::
2a. Ausleihe bereits überfällig:::
2a1. System weist die Verlängerung ab. Use Case endet ohne Erfolg.
3a. Offene Vormerkung für die Kategorie:::
3a1. System weist die Verlängerung ab. Use Case endet ohne Erfolg.
4a. Mitglied gesperrt (auch durch eine andere Ausleihe):::
4a1. System weist die Verlängerung ab. Use Case endet ohne Erfolg.
5a. Ausleihe bereits einmal verlängert:::
5a1. System weist die Verlängerung ab. Use Case endet ohne Erfolg.

Postconditions (Erfolg):: Rückgabefrist ist um eine Leihdauer verschoben; Kaution unverändert; die Ausleihe gilt als bereits verlängert und kann nicht erneut verlängert werden.

.Activity-Diagramm UC-02
[plantuml, uc-02-ausleihe-verlaengern, svg]
----
start
:Ausleihe wählen;
if (Ausleihe überfällig? [BR-AUS-07]) then (ja)
  :Verlängerung abweisen (überfällig);
  stop
endif
if (offene Vormerkung für Kategorie? [BR-AUS-07]) then (ja)
  :Verlängerung abweisen (Vormerkung offen);
  stop
endif
if (Mitglied gesperrt? [BR-AUS-08]) then (ja)
  :Verlängerung abweisen (Sperre);
  stop
endif
if (Ausleihe bereits verlängert? [BR-AUS-06]) then (ja)
  :Verlängerung abweisen (bereits verlängert);
  stop
endif
:Rückgabefrist um Leihdauer verschieben;
:Kaution unverändert lassen [BR-AUS-09];
stop
----

EARS-Anforderungen::
* REQ-UC02-01: Wenn eine überfällige Ausleihe verlängert werden soll, shall das System die Verlängerung ablehnen.
* REQ-UC02-02: Wenn für die Kategorie des Gegenstands eine offene Vormerkung besteht, shall das System die Verlängerung ablehnen.
* REQ-UC02-03: Wenn das Mitglied gesperrt ist, shall das System jede Verlängerung dieses Mitglieds ablehnen, auch für nicht überfällige Ausleihen.
* REQ-UC02-04: Wenn eine Ausleihe bereits einmal verlängert wurde, shall das System eine weitere Verlängerung derselben Ausleihe ablehnen.
* REQ-UC02-05: Wenn eine Verlängerung zulässig ist, shall das System die Rückgabefrist um die volle Leihdauer der Kategorie verschieben, ohne die hinterlegte Kaution zu ändern.

== UC-03: Gegenstand zurücknehmen

Primary Actor:: Thekendienst
Scope:: System Leihgut
Level:: User Goal
Precondition:: Die Ausleihe ist aktiv (nicht bereits zurückgegeben).
Trigger:: Ein Mitglied bringt einen Gegenstand an die Theke zurück.

Main Success Scenario::
. Thekendienst erfasst die Rückgabe der Ausleihe.
. Thekendienst erfasst optional Auffälligkeiten als Freitext (BR-RUP-02).
. System versetzt den Gegenstand in den Zustand "in Prüfung" (BR-RUP-01).
. System lässt die Ausleihe als offen bestehen, bis das Prüfprotokoll vorliegt (BR-RUP-01).

Extensions::
1a. Ausleihe bereits zurückgegeben oder bereits abgeschlossen:::
1a1. System weist die Rückgabe ab. Use Case endet ohne Erfolg.

Postconditions (Erfolg):: Gegenstand ist "in Prüfung"; Ausleihe ist weiterhin aktiv (zählt gegen das Drei-Ausleihen-Limit, BR-AUS-02); Kaution ist unverändert.

.Activity-Diagramm UC-03
[plantuml, uc-03-gegenstand-zuruecknehmen, svg]
----
start
:Ausleihe wählen;
if (Ausleihe bereits zurückgegeben/abgeschlossen?) then (ja)
  :Rückgabe abweisen;
  stop
endif
:Auffälligkeiten als Freitext erfassen (optional) [BR-RUP-02];
:Gegenstand in "in Prüfung" versetzen [BR-RUP-01];
note right: Ausleihe bleibt offen bis Prüfprotokoll vorliegt
stop
----

EARS-Anforderungen::
* REQ-UC03-01: Wenn eine bereits zurückgegebene oder abgeschlossene Ausleihe erneut zurückgegeben werden soll, shall das System die Rückgabe ablehnen.
* REQ-UC03-02: Wenn eine Rückgabe erfasst wird, shall das System den Gegenstand in den Zustand "in Prüfung" versetzen, ohne die Ausleihe abzuschließen.
* REQ-UC03-03: Während eine Ausleihe auf die Prüfung wartet, shall das System sie weiterhin gegen das Drei-Ausleihen-Limit des Mitglieds zählen.

== UC-04: Prüfung abschließen

Primary Actor:: Wart
Scope:: System Leihgut
Level:: User Goal
Precondition:: Der Gegenstand ist "in Prüfung" (Rückgabe wurde erfasst, UC-03).
Trigger:: Der Wart hat den zurückgegebenen Gegenstand kontrolliert.

Main Success Scenario::
. Wart wählt die Ausleihe des zu prüfenden Gegenstands.
. Wart erfasst das Prüfergebnis: Schäden gegenüber der bestehenden Mängelliste des Gegenstands, Zielzustand.
. System rechnet einen festgestellten Schaden der laufenden Ausleihe zu, sofern er nicht bereits in der Mängelliste aus einer früheren Prüfung vermerkt ist (BR-RUP-05).
. Wart legt den Kautionsabzug fest, höchstens in Höhe der hinterlegten Kaution (BR-KAU-02).
. System schließt die Ausleihe mit dem Prüfprotokoll ab (BR-RUP-04).
. System erhöht den Nutzungszähler des Gegenstands um eins (BR-WAR-01).
. System gibt die Kaution abzüglich des Abzugs frei und erzeugt einen Kautionsbewegungs-Eintrag (BR-KAU-01, BR-KAU-04).
. System bestimmt den Folgezustand des Gegenstands: wartungsfällig, wenn der Nutzungszähler das Wartungsintervall erreicht hat (BR-WAR-02), sonst verfügbar, sofern keine Vormerkung vorliegt.
. Liegt für die Kategorie eine Vormerkung vor und wird der Gegenstand verfügbar, reserviert das System ihn für das erste Mitglied der Warteschlange (BR-VOR-03).
. Wird der Gegenstand wartungsfällig, bleibt die Warteschlange unverändert (BR-VOR-05).

Extensions::
2a. Schaden bereits in der Mängelliste aus früherer Prüfung vermerkt:::
2a1. System rechnet den Schaden nicht der laufenden Ausleihe zu (BR-RUP-05).
4a. Kautionsabzug übersteigt hinterlegte Kaution:::
4a1. System weist die Erfassung ab. Use Case endet ohne Erfolg.
8a. Gegenstand ist irreparabel beschädigt:::
8a1. System setzt den Gegenstand auf ausgemustert statt verfügbar oder wartungsfällig (BR-RUP-06).

Postconditions (Erfolg):: Ausleihe ist abgeschlossen; Nutzungszähler erhöht; Kaution teilweise oder vollständig freigegeben; Gegenstand in genau einem Folgezustand (verfügbar, wartungsfällig, ausgemustert); ggf. neue Reservierung für die Warteschlange.

.Activity-Diagramm UC-04
[plantuml, uc-04-pruefung-abschliessen, svg]
----
start
:Ausleihe des geprüften Gegenstands wählen;
:Schäden gegenüber Mängelliste erfassen;
if (Schaden bereits in Mängelliste vermerkt? [BR-RUP-05]) then (ja)
  :Schaden nicht der Ausleihe zurechnen;
else (nein)
  :Schaden der laufenden Ausleihe zurechnen;
endif
:Kautionsabzug festlegen;
if (Abzug > hinterlegte Kaution? [BR-KAU-02]) then (ja)
  :Erfassung abweisen;
  stop
endif
:Ausleihe mit Prüfprotokoll abschließen [BR-RUP-04];
:Nutzungszähler +1 [BR-WAR-01];
:Kaution abzüglich Abzug freigeben, Bewegung buchen [BR-KAU-01, BR-KAU-04];
if (irreparabel beschädigt?) then (ja)
  :Gegenstand ausmustern [BR-RUP-06];
elseif (Nutzungszähler >= Wartungsintervall? [BR-WAR-02]) then (ja)
  :Gegenstand wartungsfällig setzen;
  :Warteschlange unverändert lassen [BR-VOR-05];
else (nein)
  :Gegenstand verfügbar setzen;
  if (Vormerkung für Kategorie vorhanden? [BR-VOR-03]) then (ja)
    :Für erstes Mitglied der Warteschlange reservieren;
  endif
endif
stop
----

EARS-Anforderungen::
* REQ-UC04-01: Wenn ein Schaden bereits in der Mängelliste des Gegenstands aus einer früheren Prüfung vermerkt ist, shall das System ihn nicht der laufenden Ausleihe zurechnen.
* REQ-UC04-02: Wenn ein Kautionsabzug die hinterlegte Kaution übersteigt, shall das System die Erfassung ablehnen.
* REQ-UC04-03: Wenn ein Prüfprotokoll erstellt wird, shall das System die zugehörige Ausleihe abschließen und den Nutzungszähler des Gegenstands um eins erhöhen.
* REQ-UC04-04: Wenn eine Prüfung abgeschlossen wird, shall das System die Kaution abzüglich des festgelegten Abzugs freigeben und einen Kautionsbewegungs-Eintrag mit Zeitstempel, Betrag und Auslöser erzeugen.
* REQ-UC04-05: Wenn der Nutzungszähler nach der Prüfung das Wartungsintervall der Kategorie erreicht, shall das System den Gegenstand auf wartungsfällig statt verfügbar setzen.
* REQ-UC04-06: Wenn ein Gegenstand nach der Prüfung verfügbar wird und eine Vormerkung für seine Kategorie vorliegt, shall das System ihn für das erste Mitglied der Warteschlange reservieren.
* REQ-UC04-07: Wenn ein Gegenstand nach der Prüfung wartungsfällig wird, shall das System die Warteschlange der Kategorie unverändert lassen.

== UC-05: Wartung abschließen

Primary Actor:: Wart
Scope:: System Leihgut
Level:: User Goal
Precondition:: Der Gegenstand ist wartungsfällig.
Trigger:: Der Wart hat die fällige Wartung durchgeführt.

Main Success Scenario::
. Wart wählt den wartungsfälligen Gegenstand.
. System setzt den Gegenstand auf verfügbar und den Nutzungszähler auf null (BR-WAR-03).
. Liegt für die Kategorie eine Vormerkung vor, reserviert das System den Gegenstand für das erste Mitglied der Warteschlange (BR-VOR-03).

Extensions::
1a. Gegenstand ist nicht wartungsfällig:::
1a1. System weist die Erfassung ab. Use Case endet ohne Erfolg.

Postconditions (Erfolg):: Gegenstand ist verfügbar (oder reserviert), Nutzungszähler ist null.

.Activity-Diagramm UC-05
[plantuml, uc-05-wartung-abschliessen, svg]
----
start
:Wartungsfälligen Gegenstand wählen;
if (Gegenstand wartungsfällig?) then (nein)
  :Erfassung abweisen;
  stop
endif
:Gegenstand verfügbar setzen, Nutzungszähler auf 0 [BR-WAR-03];
if (Vormerkung für Kategorie vorhanden? [BR-VOR-03]) then (ja)
  :Für erstes Mitglied der Warteschlange reservieren;
endif
stop
----

EARS-Anforderungen::
* REQ-UC05-01: Wenn eine Wartung für einen nicht wartungsfälligen Gegenstand abgeschlossen werden soll, shall das System die Erfassung ablehnen.
* REQ-UC05-02: Wenn eine Wartung abgeschlossen wird, shall das System den Gegenstand auf verfügbar setzen und den Nutzungszähler auf null zurücksetzen.

== UC-06: Verlust melden

Primary Actor:: Wart
Scope:: System Leihgut
Level:: User Goal
Precondition:: Eine aktive Ausleihe existiert für den verlorenen Gegenstand.
Trigger:: Der Wart erfährt (informell), dass ein ausgeliehener Gegenstand verloren ist.

Main Success Scenario::
. Wart erfasst den Verlust für die betroffene Ausleihe.
. System schließt die Ausleihe durch das Verlust-Ereignis ab, unabhängig von Rückgabe oder Prüfung (BR-VER-01, BR-VER-02).
. System behält die hinterlegte Kaution vollständig ein und bucht die Bewegung (BR-KAU-03, BR-KAU-04).
. System mustert den Gegenstand aus (BR-VER-03).

Extensions::
1a. Für den Gegenstand existiert keine aktive Ausleihe:::
1a1. System weist die Erfassung ab. Use Case endet ohne Erfolg.

Postconditions (Erfolg):: Ausleihe ist abgeschlossen (verloren); Kaution vollständig einbehalten; Gegenstand ausgemustert; keine offene Ausleihe oder Vormerkung wird durch diesen Gegenstand mehr bedient.

.Activity-Diagramm UC-06
[plantuml, uc-06-verlust-melden, svg]
----
start
:Verlust für Ausleihe erfassen;
if (aktive Ausleihe für Gegenstand vorhanden?) then (nein)
  :Erfassung abweisen;
  stop
endif
:Ausleihe durch Verlust-Ereignis abschließen [BR-VER-01, BR-VER-02];
:Kaution vollständig einbehalten, Bewegung buchen [BR-KAU-03, BR-KAU-04];
:Gegenstand ausmustern [BR-VER-03];
stop
----

EARS-Anforderungen::
* REQ-UC06-01: Wenn ein Verlust für einen Gegenstand ohne aktive Ausleihe gemeldet wird, shall das System die Erfassung ablehnen.
* REQ-UC06-02: Wenn ein Verlust gemeldet wird, shall das System die betroffene Ausleihe abschließen, ohne ein Prüfprotokoll zu verlangen.
* REQ-UC06-03: Wenn ein Verlust gemeldet wird, shall das System die hinterlegte Kaution vollständig einbehalten, einen Kautionsbewegungs-Eintrag erzeugen und den Gegenstand ausmustern.

== UC-07: Einweisung erfassen

Primary Actor:: Wart
Scope:: System Leihgut
Level:: User Goal
Trigger:: Ein Mitglied hat eine Einweisung für eine Kategorie erhalten.

Main Success Scenario::
. Wart erfasst Mitglied und Kategorie der Einweisung.
. System legt die Einweisung unbefristet an (BR-EIN-01, BR-EIN-02).

Extensions::
1a. Für dieses Mitglied und diese Kategorie besteht bereits eine gültige Einweisung:::
1a1. System weist die Erfassung als Duplikat ab.

Postconditions (Erfolg):: Mitglied kann für diese Kategorie einweisungspflichtige Gegenstände ausleihen (BR-AUS-04).

.Activity-Diagramm UC-07
[plantuml, uc-07-einweisung-erfassen, svg]
----
start
:Mitglied und Kategorie wählen;
if (gültige Einweisung bereits vorhanden?) then (ja)
  :Erfassung als Duplikat abweisen;
  stop
endif
:Einweisung unbefristet anlegen [BR-EIN-01, BR-EIN-02];
stop
----

EARS-Anforderungen::
* REQ-UC07-01: Wenn eine Einweisung erfasst wird, shall das System sie ohne Ablaufdatum anlegen.
* REQ-UC07-02: Wenn für ein Mitglied und eine Kategorie bereits eine gültige Einweisung besteht, shall das System eine erneute Erfassung als Duplikat ablehnen.

== UC-08: Einweisung widerrufen

Primary Actor:: Wart
Scope:: System Leihgut
Level:: User Goal
Precondition:: Für Mitglied und Kategorie besteht eine gültige Einweisung.
Trigger:: Der Wart entscheidet, eine Einweisung zurückzunehmen.

Main Success Scenario::
. Wart wählt die zu widerrufende Einweisung.
. System markiert die Einweisung als widerrufen (BR-EIN-03).

Extensions::
1a. Einweisung bereits widerrufen oder nicht vorhanden:::
1a1. System weist den Widerruf ab. Use Case endet ohne Erfolg.

Postconditions (Erfolg):: Einweisung gilt nicht mehr als gültig; das Mitglied erhält für diese Kategorie keine einweisungspflichtigen Gegenstände mehr, bis eine neue Einweisung erfasst wird (BR-AUS-04).

.Activity-Diagramm UC-08
[plantuml, uc-08-einweisung-widerrufen, svg]
----
start
:Einweisung wählen;
if (Einweisung gültig?) then (nein)
  :Widerruf abweisen;
  stop
endif
:Einweisung als widerrufen markieren [BR-EIN-03];
stop
----

EARS-Anforderungen::
* REQ-UC08-01: Wenn eine bereits widerrufene oder nicht vorhandene Einweisung widerrufen werden soll, shall das System den Widerruf ablehnen.
* REQ-UC08-02: Wenn eine Einweisung widerrufen wird, shall das System sie ab sofort als ungültig für BR-AUS-04 behandeln.

== UC-09: Katalog pflegen

Primary Actor:: Wart
Scope:: System Leihgut
Level:: User Goal
Trigger:: Ein Gegenstand oder eine Kategorie muss angelegt oder geändert werden.

Main Success Scenario::
. Wart legt eine Kategorie mit Leihdauer, Wartungsintervall und Einweisungspflicht an, oder ändert eine bestehende Kategorie (BR-KPF-01).
. Wart legt einen Gegenstand mit Inventarnummer, Kategorie und Wiederbeschaffungswert an, oder ändert dessen Wiederbeschaffungswert (BR-KPF-01, BR-KAT-01, BR-KAT-03).
. System wendet eine geänderte Leihdauer nur auf künftige Ausleihen an; laufende Ausleihen behalten ihre bestehende Rückgabefrist (BR-KAT-05).
. System wendet ein geändertes Wartungsintervall sofort auf den aktuellen Nutzungszähler aller Gegenstände der Kategorie an (BR-KAT-06).

Extensions::
1a. Inventarnummer bereits vergeben:::
1a1. System weist das Anlegen ab. Use Case endet ohne Erfolg.
1b. Kategorie eines Gegenstands existiert nicht:::
1b1. System weist das Anlegen ab. Use Case endet ohne Erfolg.

Postconditions (Erfolg):: Katalog enthält die neue oder geänderte Kategorie bzw. den neuen oder geänderten Gegenstand; die Kautionsberechnung (BR-KAT-04) verwendet ab sofort den aktuellen Wiederbeschaffungswert.

.Activity-Diagramm UC-09
[plantuml, uc-09-katalog-pflegen, svg]
----
start
:Kategorie oder Gegenstand anlegen/ändern;
if (Inventarnummer bereits vergeben?) then (ja)
  :Anlegen abweisen;
  stop
endif
if (Kategorie existiert nicht?) then (ja)
  :Anlegen abweisen;
  stop
endif
if (Leihdauer der Kategorie geändert? [BR-KAT-05]) then (ja)
  :Nur auf künftige Ausleihen anwenden;
endif
if (Wartungsintervall der Kategorie geändert? [BR-KAT-06]) then (ja)
  :Sofort auf aktuellen Nutzungszähler aller Gegenstände anwenden;
endif
stop
----

EARS-Anforderungen::
* REQ-UC09-01: Wenn eine Inventarnummer bereits vergeben ist, shall das System das Anlegen des Gegenstands ablehnen.
* REQ-UC09-02: Wenn die Leihdauer einer Kategorie geändert wird, shall das System sie nur auf künftig ausgegebene Ausleihen anwenden.
* REQ-UC09-03: Wenn das Wartungsintervall einer Kategorie geändert wird, shall das System es sofort auf den aktuellen Nutzungszähler aller Gegenstände dieser Kategorie anwenden.

== UC-10: Verfügbarkeit prüfen

Primary Actor:: Mitglied
Secondary Actor:: Thekendienst (kann stellvertretend abfragen)
Scope:: System Leihgut
Level:: User Goal
Trigger:: Ein Mitglied möchte wissen, ob ein Gegenstand oder eine Kategorie verfügbar ist.

Main Success Scenario::
. Mitglied fragt den Verfügbarkeitsstatus eines Gegenstands oder einer Kategorie ab.
. System liefert für jeden Gegenstand den aktuellen Zustand: verfügbar, ausgeliehen, in Prüfung, wartungsfällig, reserviert oder ausgemustert.

Extensions::
1a. Gegenstand oder Kategorie existiert nicht:::
1a1. System meldet, dass keine Daten vorliegen. Use Case endet ohne Ergebnis.

Postconditions (Erfolg):: Mitglied kennt den aktuellen Zustand, ohne dass sich der Zustand durch die Abfrage ändert.

.Activity-Diagramm UC-10
[plantuml, uc-10-verfuegbarkeit-pruefen, svg]
----
start
:Gegenstand oder Kategorie wählen;
if (existiert?) then (nein)
  :"keine Daten" melden;
  stop
endif
:Aktuellen Zustand ermitteln [BR-AUS-01, BR-WAR-04];
:Zustand zurückgeben;
stop
----

EARS-Anforderungen::
* REQ-UC10-01: Wenn ein nicht existierender Gegenstand oder eine nicht existierende Kategorie abgefragt wird, shall das System melden, dass keine Daten vorliegen.
* REQ-UC10-02: Wenn ein Gegenstand abgefragt wird, shall das System dessen aktuellen Zustand liefern, ohne ihn zu verändern.

== UC-11: Vormerkung anlegen

Primary Actor:: Mitglied
Scope:: System Leihgut
Level:: User Goal
Trigger:: Ein Mitglied möchte sich für eine Kategorie vormerken lassen, weil kein Exemplar verfügbar ist.

Main Success Scenario::
. Mitglied wählt die Kategorie.
. System prüft: Mitglied hat keine laufende Ausleihe aus dieser Kategorie (BR-VOR-07).
. System prüft: Mitglied hat noch keine offene Vormerkung für diese Kategorie (BR-VOR-08).
. System reiht die Vormerkung am Ende der Warteschlange der Kategorie ein, nach Eingangszeit (BR-VOR-01, BR-VOR-02).

Extensions::
2a. Mitglied hat bereits eine laufende Ausleihe aus dieser Kategorie:::
2a1. System weist die Vormerkung ab. Use Case endet ohne Erfolg.
3a. Mitglied hat bereits eine offene Vormerkung für diese Kategorie:::
3a1. System weist die Vormerkung ab. Use Case endet ohne Erfolg.
1a. Mitglied ist gesperrt:::
1a1. System nimmt die Vormerkung dennoch entgegen (BR-VOR-06); der Ablauf setzt sich normal fort.

Postconditions (Erfolg):: Mitglied hat einen Platz in der Warteschlange der Kategorie; eine spätere Reservierung für ein gesperrtes Mitglied wird übersprungen, ohne den Platz zu verlieren (BR-VOR-06).

.Activity-Diagramm UC-11
[plantuml, uc-11-vormerkung-anlegen, svg]
----
start
:Kategorie wählen;
if (laufende Ausleihe aus dieser Kategorie? [BR-VOR-07]) then (ja)
  :Vormerkung abweisen;
  stop
endif
if (bereits offene Vormerkung für Kategorie? [BR-VOR-08]) then (ja)
  :Vormerkung abweisen;
  stop
endif
:Vormerkung am Ende der Warteschlange einreihen [BR-VOR-01, BR-VOR-02];
note right: Sperre des Mitglieds verhindert die Vormerkung nicht [BR-VOR-06]
stop
----

EARS-Anforderungen::
* REQ-UC11-01: Wenn ein Mitglied bereits eine laufende Ausleihe aus der gewünschten Kategorie hat, shall das System die Vormerkung ablehnen.
* REQ-UC11-02: Wenn ein Mitglied bereits eine offene Vormerkung für dieselbe Kategorie hat, shall das System eine weitere Vormerkung derselben Kombination ablehnen.
* REQ-UC11-03: Wenn ein gesperrtes Mitglied eine Vormerkung anlegt, shall das System die Vormerkung annehmen.
* REQ-UC11-04: Wenn eine Vormerkung angelegt wird, shall das System sie nach Eingangszeit an das Ende der Warteschlange der Kategorie einreihen.
