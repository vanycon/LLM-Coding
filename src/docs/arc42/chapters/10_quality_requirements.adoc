[[section-quality-scenarios]]
== Qualitätsanforderungen

=== Übersicht der Qualitätsanforderungen

Diese Qualitätsanforderungen decken alle acht ISO/IEC-25010-Merkmale ab. Vier davon
konkretisieren die in <<section-introduction-and-goals>> priorisierten Top-Ziele (markiert
mit dem entsprechenden Rang); die übrigen vier sind aus dem Code und den Randbedingungen
abgeleitet, ohne eines der Top-Ziele direkt zu konkretisieren.

[options="header",cols="2,2,3"]
|===
|ISO/IEC-25010-Merkmal |Bezug |Konkretisiert

|Security |Rang 1: Sicherheit |<<qas-security>>
|Functional Suitability |Rang 2: Korrektheit der Kaution |<<qas-functional-suitability>>
|Maintainability (Analysability) |Rang 3: Nachvollziehbarkeit |<<qas-maintainability>>
|Performance Efficiency |Rang 4: Antwortzeit |<<qas-performance>>
|Reliability |Abgeleitet (Verfügbarkeit ist kein Ziel, Recoverability bleibt relevant) |<<qas-reliability>>
|Usability |Abgeleitet |<<qas-usability>>
|Compatibility |Abgeleitet |<<qas-compatibility>>
|Portability |Abgeleitet |<<qas-portability>>
|===

Jedes Szenario folgt dem sechsteiligen Schema Quelle, Stimulus, Artefakt, Umgebung, Reaktion,
Reaktionsmaß — mit einem konkreten, messbaren Reaktionsmaß statt einer vagen Zielformulierung.

=== Qualitätsszenarien

[[qas-security]]
==== Security (Rang 1: Sicherheit)

[options="header",cols="1,3"]
|===
|Teil |Ausprägung

|Quelle |Thekendienst versucht, einen Gegenstand für ein gesperrtes Mitglied auszugeben
(UC-01).
|Stimulus |Ausgabe-Anfrage für ein Mitglied mit überfälliger Ausleihe (BR-SPE-01).
|Artefakt |Ausleihe-Anwendungsdienst (<<section-building-block-view>>, Ebene 2).
|Umgebung |Regulärer Betrieb, REST- oder CLI-Kanal.
|Reaktion |Der Anwendungsdienst lehnt die Ausgabe ab, bevor ein Ausleihe-Datensatz oder eine
Kautionsbewegung entsteht.
|Reaktionsmaß |100 % der Ausgabeversuche an gesperrte Mitglieder werden abgelehnt (kein
Ausnahmefall) — geprüft durch die Gherkin-Szenarien zu BR-SPE in
link:../../specs/spec-acceptance-criteria.adoc[`spec-acceptance-criteria.adoc`], die bei jedem
Build ausgeführt werden.
|===

[[qas-functional-suitability]]
==== Functional Suitability (Rang 2: Korrektheit der Kaution)

[options="header",cols="1,3"]
|===
|Teil |Ausprägung

|Quelle |Werkstattwart schließt eine Prüfung ab (UC-04).
|Stimulus |Prüfprotokoll für einen Gegenstand mit Wiederbeschaffungswert W wird erfasst.
|Artefakt |Kaution-Domänendienst (BR-KAT-04).
|Umgebung |Regulärer Betrieb.
|Reaktion |Der Domänendienst berechnet die Kaution als 20 % von W, kaufmännisch gerundet auf
*ganze Euro* (BR-KAT-04, `prd.adoc`), gespeichert als Ganzzahl-Cent, gedeckelt auf 5–100 €, und
bucht bei sauberer Rückgabe die volle Freigabe.
|Reaktionsmaß |Für jeden Wiederbeschaffungswert zwischen 0,01 € und 10.000.000 € liegt die
berechnete Kaution exakt zwischen 5,00 € und 100,00 € (Grenzen eingeschlossen), ist ein
ganzzahliges Vielfaches von 100 Cent (ganzer Euro-Betrag) und auf den Cent exakt
reproduzierbar — geprüft durch eigenschaftsbasierte Tests (<<section-concepts>>,
Test) über diesen gesamten Wertebereich, nicht nur Beispielwerte.
|===

[[qas-functional-suitability-nebenlaeufigkeit]]
.Zweites Szenario zu Rang 2: Nebenläufige Ausgabe desselben Gegenstands
[options="header",cols="1,3"]
|===
|Teil |Ausprägung

|Quelle |Zwei Thekendienst-Vorgänge (z. B. REST und CLI, oder zwei Browser-Tabs) fast
zeitgleich am selben Vormittag.
|Stimulus |Zwei nahezu gleichzeitige Ausgabe-Anfragen (UC-01) für denselben Gegenstand treffen
innerhalb weniger Millisekunden ein.
|Artefakt |Ausleihe-Anwendungsdienst, Gegenstand-Aggregat, Persistenz-Adapter
(<<section-building-block-view>>).
|Umgebung |Regulärer Betrieb, ein Python-Prozess, eine SQLite-Datei.
|Reaktion |Genau eine der beiden Anfragen wird erfolgreich verarbeitet und legt eine Ausleihe
an; die zweite wird mit einer fachlichen Ablehnung (Gegenstand bereits ausgeliehen)
beantwortet — nie beide erfolgreich.
|Reaktionsmaß |0 doppelte aktive Ausleihen für denselben Gegenstand, erzwungen durch
ADR-007 (`BEGIN IMMEDIATE`-Transaktion mit Prüfung-und-Schreiben in einem Schritt, zusätzlich
abgesichert durch einen partiellen Unique-Index auf `Ausleihe(gegenstandId)` mit
`status = 'aktiv'`, <<section-design-decisions>>) — geprüft durch einen nebenläufigen
Service-Test, der beide Anfragen absichtlich gleichzeitig auslöst.
|===

[[qas-maintainability]]
==== Maintainability — Analysability (Rang 3: Nachvollziehbarkeit)

[options="header",cols="1,3"]
|===
|Teil |Ausprägung

|Quelle |Werkstattwart oder Vereinsvorstand untersucht nachträglich eine strittige
Kautionsauszahlung.
|Stimulus |Anfrage: "Warum wurde bei dieser Ausleihe dieser Betrag ausgezahlt?"
|Artefakt |Audit-Log (<<section-concepts>>, Observability).
|Umgebung |Nachträgliche Analyse, beliebig lange nach dem Vorgang.
|Reaktion |Jede Kautionsbewegung ist im Audit-Log mit Zeitstempel, Betrag, Auslöser (Rolle)
und Bezug zur Ausleihe auffindbar.
|Reaktionsmaß |100 % der Kautionsbewegungen und Zustandswechsel sind im Audit-Log vorhanden
(kein Fachvorgang ohne Audit-Eintrag, erzwungen durch dieselbe Transaktion,
<<section-solution-strategy>>); ein Prüfer findet die Historie eines Gegenstands oder
Mitglieds über die Aggregat-ID ohne Programmierkenntnisse anhand des Audit-Logs.
|===

[[qas-performance]]
==== Performance Efficiency (Rang 4: Antwortzeit)

[options="header",cols="1,3"]
|===
|Teil |Ausprägung

|Quelle |Thekendienst an der Theke, Samstagvormittag mit Warteschlange.
|Stimulus |Ausgabe-Anfrage (UC-01) über REST oder CLI.
|Artefakt |REST-Adapter + Anwendungskern + Persistenz-Adapter (<<section-deployment-view>>,
ein Prozess, lokale SQLite-Datei).
|Umgebung |Regulärer Öffnungsbetrieb, bis zu wenige gleichzeitige Anfragen (kein
Massenandrang laut PRD-Persona-Beschreibung).
|Reaktion |Die Anfrage wird verarbeitet und beantwortet, ohne dass der Thekendienst wartend
am Bildschirm steht.
|Reaktionsmaß |95. Perzentil der Antwortzeit unter 300 ms, gemessen serverseitig
(<<section-concepts>>, Observability) von Anfrageeingang bis Antwortversand, bei 400
Gegenständen und 800 Mitgliedern in der SQLite-Datei.
|===

[[qas-reliability]]
==== Reliability (abgeleitet — Verfügbarkeit ist kein Ziel, Recoverability bleibt relevant)

[options="header",cols="1,3"]
|===
|Teil |Ausprägung

|Quelle |Der Python-Prozess stürzt während einer laufenden Anfrage ab (z. B. Stromausfall).
|Stimulus |Prozessabbruch mitten in einer Transaktion, die mehrere Aggregate ändert (z. B.
UC-04-Kaskade).
|Artefakt |Persistenz-Adapter, SQLite-Datei.
|Umgebung |Betrieb, unerwarteter Absturz.
|Reaktion |Nach Neustart des Prozesses ist die SQLite-Datei entweder im Zustand vor oder
vollständig nach der unterbrochenen Transaktion — nie dazwischen.
|Reaktionsmaß |0 fachlich sichtbare Zwischenzustände nach Neustart (durch SQLite-Transaktions-
garantien, <<section-concepts>>, Error Handling); Wiederanlaufzeit ist die Startzeit des
Python-Prozesses (keine Reparaturschritte nötig). Verfügbarkeit selbst wird bewusst nicht
gemessen (<<section-introduction-and-goals>>).
|===

[[qas-reliability-recovery]]
.Zweites Szenario zu Reliability: Totalausfall des Vereinsrechners zwischen zwei Öffnungstagen
[options="header",cols="1,3"]
|===
|Teil |Ausprägung

|Quelle |Der Vereinsrechner oder seine Festplatte fällt zwischen zwei Öffnungstagen
vollständig aus (Hardwaredefekt, Diebstahl, Wasserschaden).
|Stimulus |Die SQLite-Datei ist auf dem Originalgerät nicht mehr zugänglich oder zerstört.
|Artefakt |Datensicherung (<<section-deployment-view>>, ADR-008).
|Umgebung |Zwischen zwei Öffnungstagen, kein laufender Betrieb.
|Reaktion |Der Verein spielt die zuletzt erstellte Tagessicherung auf einem Ersatzgerät oder
demselben Rechner nach Reparatur ein und öffnet damit spätestens zum nächsten Öffnungstag.
|Reaktionsmaß |Datenverlust ist auf höchstens einen Öffnungstag begrenzt (Sicherung erfolgt
nach jedem Öffnungstag, ADR-008); Wiederherstellung ist eine Dateikopie ohne Programmierkennt-
nisse, geprüft durch eine dokumentierte Restore-Anleitung neben dem Sicherungsskript.
|===

[[qas-usability]]
==== Usability (abgeleitet)

[options="header",cols="1,3"]
|===
|Teil |Ausprägung

|Quelle |Thekendienst ohne Programmierkenntnisse.
|Stimulus |Eine Ausgabe wird abgelehnt (Sperre, Wartungsfälligkeit, fehlende Einweisung).
|Artefakt |REST-Antwort bzw. CLI-Ausgabe (<<section-concepts>>, Error Handling).
|Umgebung |Regulärer Betrieb.
|Reaktion |Der Ablehnungsgrund erscheint als Klartext (kein Fehlercode ohne Erklärung, keine
Stacktrace).
|Reaktionsmaß |Jeder in
link:../../specs/spec-system-interfaces.adoc[`spec-system-interfaces.adoc`] dokumentierte
Fehlercode hat einen zugeordneten deutschsprachigen Klartext-Grund, der ohne Rückfrage beim
Entwicklungsteam verständlich ist (stichprobenartig durch die Personas Karim/Sabine/Rolf im
PRD geprüft).
|===

[[qas-compatibility]]
==== Compatibility (abgeleitet)

[options="header",cols="1,3"]
|===
|Teil |Ausprägung

|Quelle |Ein künftiger, heute nicht geplanter zweiter Client (z. B. ein Skript für
Statistikauswertung).
|Stimulus |Der Client möchte Katalogdaten per HTTP abrufen.
|Artefakt |REST-Adapter.
|Umgebung |Regulärer Betrieb, zusätzlicher Client neben CLI und heutigem Thekenbetrieb.
|Reaktion |Der REST-Adapter beantwortet die Anfrage über denselben dokumentierten JSON-
Vertrag, den auch die CLI nutzt — kein separates, undokumentiertes Format.
|Reaktionsmaß |Alle Endpunkte sind vollständig in
link:../../specs/spec-system-interfaces.adoc[`spec-system-interfaces.adoc`] beschrieben
(Eingabe, Statuscodes, Fehlercodes); ein neuer Client benötigt keine Änderung am
REST-Adapter, um lesend zuzugreifen.
|===

[[qas-portability]]
==== Portability (abgeleitet)

[options="header",cols="1,3"]
|===
|Teil |Ausprägung

|Quelle |Der Verein wechselt den Vereinsrechner (z. B. von Linux auf Windows).
|Stimulus |Installation des Systems auf einem neuen Rechner.
|Artefakt |Gesamtes System (<<section-deployment-view>>).
|Umgebung |Erstinstallation, kein laufender Betrieb.
|Reaktion |Das System startet mit denselben Schritten (Python-Interpreter installieren,
Abhängigkeiten installieren, Prozess starten) unabhängig vom Betriebssystem.
|Reaktionsmaß |Installation und Start sind mit denselben dokumentierten Kommandos auf Linux,
macOS und Windows möglich (reines Python + SQLite, keine plattformspezifische
Abhängigkeit, ADR-001, ADR-004); keine Migration zusätzlich zur Dateikopie der
SQLite-Datei nötig.
|===
