[[section-runtime-view]]
== Laufzeitsicht

Die folgenden Szenarien sind bewusst so gewählt, dass sie zeigen, *wie* die Bausteinsicht die
Qualitätsziele einlöst — nicht nur den Happy Path, sondern auch die Stellen, an denen eine
Regel etwas verhindert.

=== UC-01 Gegenstand ausgeben — Erfolgsfall (Sicherheit, Korrektheit der Kaution)

.Sequenzdiagramm UC-01, Erfolg
[plantuml, rt-uc01-erfolg, svg]
----
@startuml
actor Thekendienst
participant "REST-Adapter" as REST
participant "Ausleihe-Anwendungsdienst" as APP
participant "Mitglied-Aggregat" as MIT
participant "Gegenstand-Aggregat" as GEG
participant "Kaution-Domänendienst" as KAU
participant "Persistenz-Adapter" as DB

Thekendienst -> REST: POST /gegenstaende/{inv}/ausgabe
REST -> APP: ausgeben(gegenstandId, mitgliedId)
APP -> GEG: istAusgebbar()? [BR-AUS-01]
APP -> MIT: istGesperrt()? [BR-AUS-03]
APP -> MIT: aktiveAusleihen() < 3? [BR-AUS-02]
APP -> GEG: einweisungspflichtig? Einweisung vorhanden? [BR-AUS-04]
APP -> KAU: berechneKaution(wiederbeschaffungswert) [BR-KAT-04]
APP -> DB: Ausleihe anlegen, Gegenstand ausgeliehen, Audit-Eintrag [BR-AUS-05, BR-KAU-04]
DB --> APP: ok
APP --> REST: Ausleihe-DTO
REST --> Thekendienst: 201 Created
@enduml
----

=== UC-01 Gegenstand ausgeben — Ablehnung wegen Sperre (Sicherheit)

.Sequenzdiagramm UC-01, Ablehnung
[plantuml, rt-uc01-abgelehnt, svg]
----
@startuml
actor Thekendienst
participant "REST-Adapter" as REST
participant "Ausleihe-Anwendungsdienst" as APP
participant "Mitglied-Aggregat" as MIT

Thekendienst -> REST: POST /gegenstaende/{inv}/ausgabe
REST -> APP: ausgeben(gegenstandId, mitgliedId)
APP -> MIT: istGesperrt()? [BR-AUS-03]
MIT --> APP: true (überfällige Ausleihe vorhanden)
APP --> REST: Fehler MITGLIED_GESPERRT
REST --> Thekendienst: 409 Conflict
note right of REST
  Kein Schreibzugriff auf die Datenbank —
  die Ablehnung passiert vollständig im
  Anwendungskern, bevor irgendein Zustand
  verändert wird.
end note
@enduml
----

=== UC-04 Prüfung abschließen mit Reservierungskaskade (Sicherheit, Nachvollziehbarkeit)

.Sequenzdiagramm UC-04 mit Folgereservierung
[plantuml, rt-uc04, svg]
----
@startuml
actor Wart
participant "REST-Adapter" as REST
participant "Prüfung/Wartungs-Anwendungsdienst" as APP
participant "Ausleihe-Aggregat" as AUS
participant "Gegenstand-Aggregat" as GEG
participant "Kaution-Domänendienst" as KAU
participant "Warteschlange-Aggregat" as WS
participant "Persistenz-Adapter" as DB

Wart -> REST: POST /ausleihen/{id}/pruefprotokoll
REST -> APP: pruefungAbschliessen(ausleiheId, neueMaengel, abzugCent)
APP -> AUS: rechneSchadenZu(neueMaengel) [BR-RUP-05]
APP -> KAU: pruefeAbzug(abzugCent <= hinterlegteKaution) [BR-KAU-02]
APP -> AUS: abschliessen() [BR-RUP-04]
APP -> GEG: nutzungszaehlerErhoehen() [BR-WAR-01]
APP -> KAU: freigeben(kaution - abzug) [BR-KAU-01]
APP -> GEG: folgezustandBestimmen() [BR-WAR-02, BR-RUP-06]
alt Gegenstand wird verfügbar und Vormerkung vorhanden
    APP -> WS: reserviereFuerErstenInWarteschlange() [BR-VOR-03]
else Gegenstand wird wartungsfällig
    APP -> WS: keineAenderung() [BR-VOR-05]
end
APP -> DB: Prüfprotokoll, Kautionsbewegung, Audit-Einträge speichern (eine Transaktion)
DB --> APP: ok
APP --> REST: Prüfprotokoll-DTO
REST --> Wart: 201 Created
@enduml
----

Alle Schreibvorgänge dieses Szenarios laufen in *einer* Datenbanktransaktion (siehe
<<section-concepts>>, Error Handling) — entweder wird die Ausleihe abgeschlossen, der
Nutzungszähler erhöht, die Kaution gebucht *und* die Reservierung vergeben, oder keines davon.
Das verhindert einen Zwischenzustand, in dem die Kaution schon gebucht, die Reservierung aber
noch offen ist (Qualitätsziel Nachvollziehbarkeit).

=== Sperre als abgeleitetes Prädikat (Systemreaktion BR-SPE)

.Sequenzdiagramm Sperre-Berechnung zur Anfragezeit
[plantuml, rt-sperre, svg]
----
@startuml
participant "Ausleihe-Anwendungsdienst" as APP
participant "Mitglied-Aggregat" as MIT
participant "Zeitquelle-Adapter" as CLK
participant "Persistenz-Adapter" as DB

APP -> MIT: istGesperrt(mitgliedId)
MIT -> CLK: heute()
CLK --> MIT: Datum
MIT -> DB: ladeAktiveAusleihen(mitgliedId)
DB --> MIT: Ausleihen[]
MIT -> MIT: existiert Ausleihe mit rueckgabefrist < heute\nund zustand not in {zurueckgegeben, abgeschlossen}? [BR-SPE-02]
MIT --> APP: gesperrt: true/false
@enduml
----

Es gibt keinen eigenen Endpunkt, der eine Sperre "auslöst" — sie wird bei jeder Ausgabe- und
Verlängerungsprüfung sowie bei jeder Reservierungsvergabe neu aus dem aktuellen Datum
berechnet. Das ist dieselbe austauschbare Zeitquelle, die auch Rückgabefristen und
Reservierungsverfall bestimmt (ADR-006) — ein einziger Ort, an dem "heute" definiert wird,
macht Fristen über alle Anwendungsfälle hinweg konsistent testbar.
