Dieses Diagramm wird aus dem Bausteinsicht-Modell
link:../bausteinsicht/architecture.jsonc[`architecture.jsonc`] generiert (Ansicht
`context-business`); es ist also nicht mehr von Hand gepflegt, sondern über
`bausteinsicht sync` bzw. `bausteinsicht export-diagram` aus derselben Quelle erzeugt, die auch
das draw.io-Diagramm speist. Externe Systeme fehlen bewusst: kein Zahlungsanbieter, kein
Mailversand, keine Mitgliederverwaltung (PRD, "Nicht-Ziele").

Diese drei Rollen und ihre Anwendungsfälle sind in link:../../specs/spec.adoc[`spec.adoc`],
Abschnitt "Akteure" und "Anwendungsfall-Katalog" spezifiziert. Es gibt bewusst keine externen
Systeme im Kontext — das ist eine direkte Folge der PRD-Nicht-Ziele (keine Kassenführung, kein
Online-Shop, keine Mitgliederverwaltung) und vereinfacht die Sicherheits- und Fehlerbehandlungs-
Konzepte in <<section-concepts>> erheblich: es gibt keine Integration, die eine Anti-Corruption-
Layer bräuchte.

[options="header",cols="1,3"]
|===
|Kanal |Ein-/Ausgabe

|REST-API |JSON über HTTP, siehe link:../../specs/spec-system-interfaces.adoc[`spec-system-interfaces.adoc`]
für jeden Endpunkt (Eingabe, Validierung, Statuscodes, Fehlercodes).
|CLI |Kommandozeilenargumente, die 1:1 auf REST-Aufrufe abgebildet werden (ADR-005); keine
Ausgabe/Verarbeitung, die nicht auch über REST erreichbar wäre (bestätigte Abgrenzung,
`prd-klaerungen.adoc`).
|===

Diese Aufteilung in zwei Kanäle, die auf denselben Anwendungskern zugreifen, ist bereits eine
Antwort auf das Qualitätsziel *Sicherheit*: Geschäftsregeln existieren nur an einer Stelle
(Anwendungskern), nicht dupliziert in CLI und REST — es kann nicht sein, dass ein Kanal eine
Regel prüft und der andere nicht.
