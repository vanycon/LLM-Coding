= EPIC-C: Einweisung — Analyse (vor Implementierung)

== Scope & Architektur

Umfasst UC-07 (Einweisung erfassen) und UC-08 (Einweisung widerrufen).

Neues Aggregate: **Einweisung** (mitglied_id, kategorie_id, erstellt_am, widerrufen_am)
- Single-Aggregate State Machine (wie EPIC-A2, kein Cross-Aggregate-Port nötig)
- Repository: EinweisungRepository (find_by_id, find_gueltige_je_mitglied_kategorie, insert, update)
- Duplikat-Schutz: Unique Index auf (mitglied_id, kategorie_id) WHERE widerrufen_am IS NULL (BR-EIN-01, bereits in schema.sql)

== Validierungsreihenfolge (nach SI-07, SI-08)

=== UC-07 Einweisung erfassen (POST /einweisungen, SI-07)

SI-07 sagt nicht explizit die Reihenfolge, aber konsistent mit anderen SIs:

1. Kategorie existiert (404 KATEGORIE_NICHT_GEFUNDEN)
2. Gültige Einweisung für (Mitglied, Kategorie) existiert nicht (409 DUPLIKAT — BR-EIN-01, REQ-UC07-02)

Bei Erfolg: Einweisung mit erstellt_am = jetzt, widerrufen_am = NULL anlegen.

=== UC-08 Einweisung widerrufen (DELETE /einweisungen/{einweisungId}, SI-08)

SI-08 sagt: "Einweisung bereits widerrufen oder nicht vorhanden" → 404 oder 409?
Interpretation: 
- Einweisung nicht vorhanden → 404 EINWEISUNG_NICHT_GEFUNDEN
- Einweisung bereits widerrufen (widerrufen_am IS NOT NULL) → 409 BEREITS_WIDERRUFEN

Validierungsreihenfolge:
1. Einweisung existiert & gültig (404)
2. Noch nicht widerrufen (409)

Bei Erfolg: widerrufen_am = jetzt, Einweisung bleibt in DB (Audit Trail).

=== Integration: einweisung_erfassen() (UC-07)

Port-Zugriffe:
1. kategorie_repo.find_by_id(kategorie_id) — check exists
2. einweisung_repo.find_gueltige_je_mitglied_kategorie(mitglied_id, kategorie_id) — check duplikat
3. einweisung_repo.insert(new_einweisung)

Rückgabewert: `Einweisung | EinweisungAblehnung` (Union-Type)

Rejection-Dataclasses:
- `KategorieNichtGefunden(kategorie_id)` → 404
- `DuplikatEinweisung(mitglied_id, kategorie_id)` → 409 DUPLIKAT

=== Integration: einweisung_widerrufen() (UC-08)

Port-Zugriffe:
1. einweisung_repo.find_by_id(einweisung_id) — check exists & valid
2. einweisung_repo.update(widerrufen_einweisung)

Rejection-Dataclasses:
- `EinweisungNichtGefunden(einweisung_id)` → 404
- `BereitsWiderrufen(einweisung_id)` → 409

== Design-Entscheidungen

**Warum kein Mitglied-Check bei UC-07?**
- Mitglied-Verwaltung ist außerhalb dieses Systems (PRD: "Mitglied hat nur mitgliedId und abgeleitetes gesperrt-Flag")
- Jede mitglied_id akzeptieren und im System speichern (Audit Trail)
- Wenn Mitglied unbekannt: wird die Einweisung trotzdem angelegt, nützt aber nichts (führt bei UC-01 zur Ablehnung)

**Warum widerrufen_am statt DELETE?**
- Append-only Audit Log Pattern (ADR-009, 08_concepts.adoc)
- Vollständige Historie: Wann wurde die Einweisung angelegt, wann widerrufen
- Query: Gültige Einweisung = `widerrufen_am IS NULL`

**Duplikat-Kontrolle: Unique Index vs. Service-Level?**
- Unique Index auf (mitglied_id, kategorie_id) WHERE widerrufen_am IS NULL (DB-erzwungen, ADR-007 Pattern)
- Service-Level Check ZUSÄTZLICH (Fehler abfangen, bevor SQLite IntegrityError wirft)
- REST gibt explizit 409 DUPLIKAT statt 500 zu

== REST Endpunkte

=== POST /einweisungen (UC-07, SI-07)

Request Body:
```json
{
  "mitgliedId": "m1",
  "kategorieId": "cat-1"
}
```

Responses:
- 201 Created: `{ einweisungId, mitgliedId, kategorieId, erstelltAm }`
- 404 KATEGORIE_NICHT_GEFUNDEN
- 409 DUPLIKAT
- 403 ROLLE_NICHT_BERECHTIGT (nur Wart)

=== DELETE /einweisungen/{einweisungId} (UC-08, SI-08)

Responses:
- 204 No Content (oder 200 mit Einweisung-Objekt)
- 404 EINWEISUNG_NICHT_GEFUNDEN
- 409 BEREITS_WIDERRUFEN
- 403 ROLLE_NICHT_BERECHTIGT (nur Wart)

== Test-Strategie

**Unit Tests** (Operationen):
- _einweisung_validieren: eigentlich trivial, kann Skip sein

**Integration Tests** (Service-Layer):
- einweisung_erfassen: Erfolg, Kategorie nicht gefunden, Duplikat
- einweisung_widerrufen: Erfolg, nicht gefunden, bereits widerrufen

**REST Tests**:
- POST /einweisungen: Erfolg, 404 Kategorie, 409 Duplikat, 403 Rolle
- DELETE /einweisungen/{id}: Erfolg, 404 nicht gefunden, 409 bereits widerrufen, 403 Rolle

**Ziel: ~8–10 Tests total**

== Known Gaps & Unresolved Questions

- Wederruf-Logik ist simpel (nur widerrufen_am setzen). Keine explizite "Reversals" oder "Reactivate" — widerrufen ist terminal.
- Einweisung-Check bei UC-01 (Ausgabe, EPIC-A): aktuell auf Stub (check BR-AUS-04, uncomment mit EPIC-C completion)
- Audit Log: Noch nicht geklärt, ob einweisung_erfassen / einweisung_widerrufen Events ins audit_log schreiben sollen (wie UC-04 pruefung_abgeschlossen). Für jetzt: Audit Trail nur über widerrufen_am Timestamp.
