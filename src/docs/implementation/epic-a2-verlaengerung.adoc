== User Story A2.1 — Ausleihe verlängern (UC-02)

Als *Thekendienst* möchte ich eine bestehende Ausleihe verlängern können, damit ein Mitglied
einen Gegenstand länger behalten kann, sofern keine Vormerkung eines anderen Mitglieds
entgegensteht.

* Referenz: UC-02 (`spec-use-cases.adoc`).
* Akzeptanzkriterien: `ausleihe-verlaengern.feature` (`spec-acceptance-criteria.adoc`).
* Priorität: *Should*.
* Abhängigkeit: benötigt EPIC-A (UC-01) und, für den Ablehnungspfad "Vormerkung eines
  anderen Mitglieds", EPIC-E (UC-11) — kann technisch vor EPIC-E begonnen werden, der
  Ablehnungspfad ist aber erst mit EPIC-E vollständig testbar.

=== Analyse (vor Implementierung)

**Scope & Architektur:**
- Nur UC-02 implementiert; UC-05 (Wartung) und UC-06 (Verlust) gehören zu EPIC-B2
- UC-02 ist ein simpler State-Transition-Service: Ausleihe (aktiv) → Ausleihe (aktiv, verlaengert=true, rueckgabefrist verschoben)
- Service braucht nur `AusleiheRepository` (aus EPIC-A) und `KategorieRepository` (aus EPIC-D)
- Kein neuer Port nötig: Ausleihe-Update kann direkt via `ausleihe_repo.update()` erfolgen (IOSP: Operation = Validierung, Integration = Repos + Update)

**Validierungsreihenfolge (SI-02, exakt in dieser Reihenfolge):**
1. Ausleihe existiert & ist im Zustand `aktiv` (404 AUSLEIHE_NICHT_GEFUNDEN)
2. Ausleihe nicht überfällig (409 AUSLEIHE_UEBERFAELLIG, BR-AUS-07) — Rückgabefrist < heute
3. Keine offene Vormerkung für Kategorie (409 VORMERKUNG_OFFEN, BR-AUS-07) — **DEFERRED zu EPIC-E**: Für jetzt: wenn das Feld `reservierungen_offen` in Kategorie nicht existiert, immer True (kein Fehler); mit EPIC-E wird die echte Check implementiert
4. Mitglied nicht gesperrt (409 MITGLIED_GESPERRT, BR-AUS-08) — prüfe `mitglied_gesperrt` in Ausleihe
5. Ausleihe noch nicht verlängert (409 BEREITS_VERLAENGERT, BR-AUS-06) — `ausleihe.verlaengert == False`

**Verarbeitung:**
- Berechne neue Rückgabefrist: `heute + kategorie.leihdauer_tage`
- Markiere Ausleihe: `verlaengert = True`
- Kaution bleibt unverändert (BR-AUS-09)
- Update in eine Transaktion: Ausleihe-Update (falls nötig: Audit-Log, derzeit noch nicht Requirement für UC-02)
- Zurückgabe: aktualisierte Ausleihe (200 OK) mit allen Feldern

**REST-Endpunkt:**
- `POST /ausleihen/{ausleiheId}/verlaengerung` (Thekendienst-Rolle erforderlich)
- Eingabe: nur ausleiheId im Pfad, kein Request-Body
- Status: 200 OK (nicht 201, weil Ressource bereits existiert — nur Update)
- Response: vollständige Ausleihe (wie SI-01 POST /gegenstaende/{inv}/ausgabe)
- Fehler-Mapping: siehe Validierungsreihenfolge oben

**Known Gaps / Design-Entscheidungen:**
- Vormerkung-Check ist noch ein Stub (erst mit EPIC-E funktional) — dokumentiert im Service
- Kein atomare Multi-Objekt-Transaktion nötig wie in EPIC-B (nur ein Aggregat: Ausleihe)
- Sperrung-Check nutzt das Feld `mitglied_gesperrt` direkt aus Ausleihe (schon in UC-01 vorhanden)

**Test-Abdeckung:**
- Validierung: 5 Ablehnung-Pfade (überfällig, Vormerkung, gesperrt, schon verlängert, nicht gefunden)
- Happy Path: erfolgreiche Verlängerung, Felder-Update prüfen
- REST: Endpunkt-Tests mit Rollen-Prüfung, Status-Codes
- DB: Datum-Berechnung verifizieren
