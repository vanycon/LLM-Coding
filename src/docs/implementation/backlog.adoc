= Backlog Release 1 — Leihgut
:toc:

Dieses Backlog leitet EPICs und User Stories aus der Spezifikation
(link:../specs/spec-use-cases.adoc[`spec-use-cases.adoc`],
link:../specs/spec-domain-model.adoc[`spec-domain-model.adoc`]) ab. Es liegt bewusst als
Datei im Repository, nicht als GitHub Issues (Absprache mit dem Nutzer). Jede Story nennt ihre
Use-Case- und Business-Rule-IDs zur Rückverfolgung.

== Walking Skeleton (erster Schnitt)

Bevor ein EPIC begonnen wird, steht ein einziger, dünner End-zu-Ende-Schnitt durch alle
Schichten (REST-Adapter → Anwendungskern → Persistenz-Adapter → SQLite), der so wenig wie
möglich Fachlogik trägt:

[[skeleton-01]]
*Skeleton-01 — Verfügbarkeit eines Gegenstands abfragen (Teilmenge von UC-10)*::
`GET /gegenstaende/{id}/verfuegbarkeit` liefert `verfügbar`/`nicht verfügbar` aus einer
echten SQLite-Tabelle, ohne Rollenprüfung, ohne Vormerklogik, ohne CLI. Zweck: beweisen, dass
FastAPI, der Anwendungskern-Port `GegenstandRepository` und die SQLite-Datei
(inkl. Schema-DDL) zusammenspielen — nicht, fachlichen Wert zu liefern. Wird verworfen bzw.
durch EPIC-D vollständig ersetzt, sobald dieser beginnt.

Erst danach beginnt EPIC-D als erster echter EPIC (Katalog ist Voraussetzung für alles
andere: ohne Gegenstände keine Ausgabe).

== Priorisierung (MoSCoW) und Reihenfolge

[options="header",cols="1,3,1,3"]
|===
|EPIC |Titel |Priorität |Begründung / Abhängigkeit

|EPIC-D |Katalog & Verfügbarkeit |Must |Voraussetzung für alle anderen EPICs (kein
Gegenstand ohne Katalogeintrag); enthält den Walking Skeleton.
|EPIC-C |Einweisung |Must |BR-AUS-04 (UC-01) prüft eine gültige Einweisung — EPIC-A kann
für einweisungspflichtige Kategorien ohne EPIC-C nicht vollständig getestet werden.
Widerruf (UC-08) kann als Should nachgezogen werden, Erfassen (UC-07) ist Must.
|EPIC-A |Ausleihe-Kernprozess (Ausgabe, Rücknahme) |Must |Kernnutzen des Systems
(PRD, Erfolgskriterium "Ausleihvorgang unter 30 Sekunden").
|EPIC-B |Prüfung & Kaution |Must |Trägt Qualitätsziel 2 (Korrektheit der Kaution) —
höchste Priorität laut Qualitätszielen; ohne Prüfabschluss bleibt jede Ausgabe offen.
|EPIC-A2 |Verlängerung |Should |Komfortfunktion, keine Ausgabe/Rücknahme blockiert ohne sie.
|EPIC-E |Vormerkung |Should |Erfolgskriterium "vergebliche Wege unter 2 %" hängt daran,
ist aber ohne Grundprozess (EPIC-A/B) nicht sinnvoll umsetzbar.
|EPIC-B2 |Wartung & Verlust |Could |Seltener Pfad (Wartungsfälligkeit, Verlust), baut auf
EPIC-B auf.
|===

Abhängigkeiten zusammengefasst: `EPIC-D → EPIC-C → EPIC-A → EPIC-B → (EPIC-A2, EPIC-E) →
EPIC-B2`. `EPIC-C` und `EPIC-D` können parallel begonnen werden, da sie unterschiedliche
Aggregate betreffen (Katalog/Gegenstand vs. Einweisung/Mitglied); `EPIC-A` benötigt aber
beide, bevor es vollständig (inkl. Ablehnungspfad BR-AUS-04) abgeschlossen werden kann.

== Nicht im Backlog enthalten

* Web-Oberfläche/Mitglieder-Kiosk — siehe `prd.adoc`, "Ausblick: Release 2 (Kandidat)"; kein
  EPIC, solange nicht eigens spezifiziert.
* Infrastruktur-Aufgaben ohne eigenen fachlichen Wert (z. B. CI-Pipeline einrichten,
  Projektgerüst anlegen) sind keine User Stories, sondern werden als technische
  Voraussetzung vor Skeleton-01 erledigt, nicht separat priorisiert.
