= EPIC-E: Vormerkung (UC-05 / SI-05) – Analyse

== Scope

**UC-05: Vormerkung erfassen** (Mitglied reserviert Kategorie)
- Preconditions: Kategorie existiert, Mitglied nicht bereits reserviert (diese Kategorie)
- Main Success: Vormerkung mit Status `offen`, Reihenfolge = count(offene) + 1
- Postcondi tions: Vormerkung in Datenbank, REST returns 201 mit ID

**UC-08 Sub (Automatikmechanik):** Nach Rückgabe (UC-03) Gegenstand verfügbar
- System prüft: gibt es offene Vormerkung für diese Kategorie?
- Wenn ja (erste nach Reihenfolge): setze Status = `automatisch_abgesagt`, ggf. Benachrichtigung
- Wenn weitere offen: nächste rückt auf Platz 1

Nicht in EPIC-E implementiert, aber als Stub in `gegenstand_zuruecknehmen()` vorbereitet:
- **UC-05 Extension (BR-VOR-03):** 7-Tage-Automatik-Absage (später via Batch-Job)

== Bounded Context: Vormerkung Aggregate

```
Vormerkung:
  - vormerkung_id: UUID (Primary Key)
  - kategorie_id: str (FK)
  - mitglied_id: str (FK)
  - erstellt_am: str (ISO-Timestamp)
  - status: enum["offen", "automatisch_abgesagt", "manuell_abgesagt"]
  - reihenfolge: int (1, 2, 3, ... für diese Kategorie)
```

**Regeln:**
- BR-VOR-01: Max 1 offene Vormerkung je (Mitglied, Kategorie)
  - DB: Unique Index on (mitglied_id, kategorie_id) WHERE status = 'offen'
- BR-VOR-02: Reihenfolge bestimmt Zugriff (FIFO, smallest reihenfolge = nächste)
- BR-VOR-03: Auto-Absage nach 7 Tagen (Batch-Job; Scope nicht in EPIC-E)

**State Machine:**
```
offen
  ↓ (Mitglied reißt Platz → UC-05 nicht möglich)
  ↓ (Auto-Absage nach 7d) → automatisch_abgesagt
  ↓ (Admin/Hintergrund) → manuell_abgesagt
```

== Validierungsreihenfolge (SI-05)

**UC-05.1: Vormerkung erfassen**
1. Kategorie existiert? → 404 `KATEGORIE_NICHT_GEFUNDEN`
2. Mitglied nicht gesperrt? → 409 `MITGLIED_GESPERRT` (NEW, BR-VOR-04)
3. Keine offene Vormerkung für diese (M, K)? → 409 `DUPLIKAT_VORMERKUNG` (BR-VOR-01)
4. INSERT: Neue Vormerkung mit Status=offen, Reihenfolge=next

**Errors mapped to HTTP:**
- `KategorieNichtGefunden` → 404
- `MitgliedGesperrt` → 409
- `DuplikatVormerkung` → 409

**UC-05.2: Vormerkung abrufen (Status-Query)**
- GET /vormerkungen/{vormerkungId}
- Gibt 200 + Body, oder 404 wenn nicht vorhanden
- Rolle: `lesend_erlaubt` (thekendienst, mitglied, wart)

== Database Schema

```sql
CREATE TABLE vormerkung (
  vormerkung_id TEXT PRIMARY KEY,
  kategorie_id TEXT NOT NULL,
  mitglied_id TEXT NOT NULL,
  status TEXT NOT NULL CHECK(status IN ('offen', 'automatisch_abgesagt', 'manuell_abgesagt')),
  reihenfolge INTEGER NOT NULL,
  erstellt_am TEXT NOT NULL,
  FOREIGN KEY(kategorie_id) REFERENCES kategorie(kategorie_id),
  UNIQUE(mitglied_id, kategorie_id) WHERE status = 'offen'
);

CREATE INDEX ix_vormerkung_kategorie_offen 
  ON vormerkung(kategorie_id, reihenfolge) 
  WHERE status = 'offen';
```

**Bemerkung:** Unique Index nur auf offen Vormerkungen (BR-VOR-01).
Abgesagte Vormerkungen blockieren keine Neuerfassung.

== Risks & Decisions

- **Reihenfolge Berechnung:** count(offene für diese Kategorie) + 1. Race condition möglich (zwei gleichzeitig erfassen → beide Reihenfolge=2). Mitigiert durch: (a) DB Unique Index, (b) Service re-query nach Insert.
- **Automatische Absage:** Stub, damit EPIC-A Rückgabe grün bleibt. Echte Implementierung später via Event/Job.
- **Mitglied gesperrt Prüfung:** Über `ausleihe_repo.is_mitglied_gesperrt()` wie in EPIC-A. Leihgut kennt nur Status `mitglied_gesperrt`, nicht den Mitglied-Stammsatz.
- **Keine Mitglied-Validierung:** Wie EPIC-C: unbekannte mitglied_id wird akzeptiert.

== Akzeptanzkriterien (Gherkin)

**Szenario: Vormerkung für verfügbare Kategorie erfassen**
```
Given eine Kategorie "Kettensäge" existiert
  And ein Mitglied "M-7" existiert und ist nicht gesperrt
  And keine offene Vormerkung von M-7 für Kettensäge
When M-7 erfasst eine Vormerkung für Kettensäge
Then erhält die Vormerkung Status "offen"
  And erhält Reihenfolge 1
  And die Antwort ist 201 Created
```

**Szenario: Doppelte Vormerkung wird abgelehnt**
```
Given eine Kategorie existiert
  And M-7 hat bereits eine offene Vormerkung für diese Kategorie
When M-7 versucht eine zweite Vormerkung für die gleiche Kategorie zu erfassen
Then erhält er 409 Conflict
  And der fehlercode ist "DUPLIKAT_VORMERKUNG"
```

**Szenario: Reihenfolge wird korrekt inkrementiert**
```
Given eine Kategorie und 3 offene Vormerkungen (Reihenfolge 1, 2, 3)
When M-9 erfasst eine neue Vormerkung für diese Kategorie
Then erhält die neue Vormerkung Reihenfolge 4
```
