= EPIC-D: Katalog & Verfügbarkeit
:toc:

Voraussetzung für alle anderen EPICs: ohne Gegenstände im Katalog gibt es nichts auszugeben.
Enthält auch den Walking Skeleton (siehe `backlog.adoc`).

== User Story D1 — Katalog pflegen (UC-09)

Als *Wart* möchte ich Gegenstände und Kategorien anlegen und ändern können, damit der
Bestand des Vereins im System abgebildet ist, bevor irgendetwas ausgeliehen werden kann.

* Referenz: UC-09 (`spec-use-cases.adoc`), BR-KAT-01 bis BR-KAT-04
  (`spec-domain-model.adoc`).
* Akzeptanzkriterien: `katalog-pflegen.feature` (`spec-acceptance-criteria.adoc`).
* INVEST-Hinweis: unabhängig umsetzbar (kein weiteres EPIC nötig), klein genug für einen
  Feature-Branch (ein Aggregat: `Gegenstand`/`Kategorie`).
* Enthält die Kautionsberechnung nach BR-KAT-04 (kaufmännisch gerundet auf ganze Euro,
  siehe `spec-domain-model.adoc`, Validierungsregeln) — Property-Test über einen
  Wertebereich von Wiederbeschaffungswerten ist Teil der Definition of Done dieser Story,
  nicht optional (PRD, "Definition of Done").

== User Story D2 — Verfügbarkeit prüfen (UC-10)

Als *Mitglied* (über den Thekendienst als Mittler) möchte ich erfahren, ob ein Gegenstand
gerade verfügbar ist, damit ich nicht vergeblich zur Ausleihe komme.

* Referenz: UC-10 (`spec-use-cases.adoc`).
* Akzeptanzkriterien: `verfuegbarkeit-pruefen.feature` (`spec-acceptance-criteria.adoc`).
* INVEST-Hinweis: rein lesend, keine Fachlogik außer Statusermittlung — deshalb als
  Walking-Skeleton-Kandidat gewählt (siehe `backlog.adoc`, Skeleton-01).
* Erfolgskriterium (PRD): "vergebliche Wege bei Vormerkung unter 2 %" hängt indirekt an einer
  korrekten Verfügbarkeitsauskunft.

== Reihenfolge innerhalb des EPICs

D1 vor D2: Ohne angelegte Gegenstände lässt sich Verfügbarkeit nicht sinnvoll testen (leere
Datenbank liefert immer "nicht gefunden"). Der Walking Skeleton (Skeleton-01) darf trotzdem
vor D1 stehen, weil er absichtlich noch keinen echten Katalog voraussetzt, sondern mit einem
einzelnen testweise angelegten Datensatz arbeitet.
