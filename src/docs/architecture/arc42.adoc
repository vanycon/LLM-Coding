== 1. Introduction and Goals

=== 1.1 Requirements Overview

Leihgut is a local lending system for a library of things. It supports counter staff issuing and extending loans, counter staff receiving returned items, workshop technicians inspecting and maintaining items, and members creating and resolving category-based holds.

The system replaces a paper binder and an untraceable cash-deposit process with a single source of truth for item availability, member borrowing eligibility, inspection outcomes, maintenance status, holds, reservations, and deposit transactions.

The architecture must preserve these domain distinctions:

* A returned item is in inspection; it is not immediately available.
* A deposit is safeguarded money, not a fee or revenue.
* Eligibility depends on both item and member state.
* Maintenance is driven by completed-loan count, not elapsed time.
* A hold is a category queue; a reservation is a temporary allocation of an item.

=== 1.2 Quality Goals

The following goals are architectural drivers from the PRD:

[cols="1,3,3"]
|===
|Priority |Quality goal |Architectural response

|1 |Security: a member without required instruction cannot issue an item through any interface. |One application service and one domain eligibility policy are shared by REST and CLI; adapters cannot bypass them.

|2 |Deposit correctness: recalculating a loan balance from 50 completed loans deviates by 0 cents. |Money is represented as integer euro cents; deposit transactions are immutable and committed atomically with the use case.

|3 |Traceability: an inspection deduction is reconstructable. |Append-only audit entries and immutable deposit transactions reference the triggering operation and affected loan.

|4 |Response time: eligibility completes under 300 ms at the 95th percentile for 100 calls with 400 items and 800 members. |Eligibility uses indexed reads and a read-only application path without writes or external calls.
|===

Availability is deliberately not an architectural goal: the association opens twice per week and the system has no external service dependency.

== 2. Architecture Constraints

=== 2.1 Product Constraints

* Release 1 is a single local process.
* All use cases are exposed through a REST API.
* Workshop technician tasks additionally have a `leihgut` CLI.
* There is no web UI, online shop, shipping, cash management, member management, login, email, payment integration, cloud dependency, or external service.

=== 2.2 Technical and Contract Constraints

* REST uses the contracts in `src/docs/specs/system-interfaces.adoc`.
* CLI output is JSON on standard output; validation and domain errors use the common error shape on standard error and exit status 1.
* Identifiers are opaque strings.
* Dates are ISO 8601 calendar dates. Timestamps are UTC ISO 8601 instants.
* Monetary values are integer euro cents.
* The caller supplies a role through `X-Role` or `--role`; authentication and role verification are outside release 1. Missing or unsupported roles are still rejected.
* Every state-changing operation is atomic.
* The system uses a replaceable time source for today's date.

=== 2.3 Architectural Constraints

* The domain model is independent of REST, CLI, persistence, and clock implementations.
* Layer boundaries expose DTOs and contracts, never domain entities.
* Mapping is explicit at each boundary.
* Dependency direction points inward through ports; infrastructure implements those ports.
* PlantUML diagrams use the bundled C4-PlantUML standard library.

=== 3.3 Scope Boundaries

Inside the system:

* Catalog and category policy.
* Member borrowing state, instructions, loans, returns, and inspections.
* Deposit calculation and immutable deposit ledger.
* Usage counters, maintenance state, and retirement.
* Category hold queues and item reservations.
* Audit trail and current-date evaluation.

Outside the system:

* Authentication and identity proof.
* Membership fees, joining, leaving, and member master-data administration.
* Physical cash handling and reconciliation with a cash drawer.
* Email or other notifications.
* Shipping, payment processing, and online commerce.

== 4. Solution Strategy

=== 4.1 Architectural Style

Use a modular monolith with hexagonal boundaries:

* A single process and local transactional database minimize operational cost and preserve atomicity.
* REST and CLI are thin inbound adapters.
* Application services implement use-case orchestration and transaction demarcation.
* The domain core owns invariants and produces decisions or domain events.
* Persistence is an outbound adapter behind repository and unit-of-work ports.
* Audit and deposit recording are mandatory ports used by every state-changing service.

=== 4.2 Key Strategies

* Re-evaluate issue eligibility inside the issue transaction; eligibility responses are advisory and can become stale.
* Use integer cents and explicit deposit transaction types; never use floating-point money.
* Model loan completion as an inspection action, not as the counter return action.
* Treat holds and reservations as separate concepts and persist queue order by receipt timestamp plus stable hold identifier.
* Use a replaceable clock so overdue and three-calendar-day expiry behavior is deterministic in tests.
* Resolve reservation expiry through an explicit command in release 1. Lazy evaluation may be added only after the contract is clarified.
* Use optimistic locking or equivalent write-conflict detection to prevent double issue, duplicate return, duplicate inspection, and competing reservation allocation.

=== 5.3 Domain Ports

Inbound application commands and results are DTOs. Outbound ports are interfaces owned by the application/domain boundary:

* `ItemRepository`, `CategoryRepository`, `MemberRepository`, `LoanRepository`, `HoldRepository`, and `ReservationRepository`.
* `InspectionRepository` for reports and previous inspection history.
* `DepositLedger` for immutable transaction append and balance reads.
* `AuditLog` for append-only state-change records.
* `UnitOfWork` for atomic commit and rollback.
* `Clock` for current date and UTC timestamp.

Repositories return domain snapshots or aggregates through explicit mappers. Adapters do not expose database records to the domain.

=== 6.2 Return and Inspect Item

. `ReturnLoanService` verifies an active loan without a prior return.
. It records counter observations, changes the item to `IN_INSPECTION`, and changes the loan to `AWAITING_INSPECTION`.
. `InspectLoanService` loads the returned loan and history, creates exactly one report, attributes damage, and calculates the final deposit outcome.
. It increments usage exactly once, selects `AVAILABLE`, `DUE_FOR_MAINTENANCE`, or `RETIRED`, and allocates a reservation only for an available item.
. It appends audit and deposit records and recalculates member suspension in the same transaction.

=== 6.3 Reservation Expiry

The explicit expiry command loads active reservations whose calendar expiry has been reached. Each reservation is resolved in queue order. A suspended member is skipped without deleting the hold or changing queue position. The next eligible member receives a three-calendar-day reservation; if none exists, the item becomes available.

=== 6.4 Concurrency Scenarios

* Two issue requests for the same item: the transaction that commits first changes the item state; the other receives a conflict and writes no loan or deposit transaction.
* Two inspection requests for the same returned loan: a unique report constraint and state check allow exactly one completion.
* Concurrent hold allocation: queue ordering and a write lock or optimistic version check allow one reservation per item.
* A stale eligibility response: issue re-evaluates all conditions, so a stale read cannot authorize a loan.

== 8. Crosscutting Concepts

=== 8.1 Threat Model

[cols="1,2,3,2"]
|===
|ID |STRIDE threat |Exposure |Mitigation

|T-001 |Spoofing |Caller supplies role header or CLI flag without authentication. |Make authentication exclusion explicit; reject missing/unsupported roles; deploy on the trusted local workstation; do not present this as identity verification.
|T-002 |Tampering |A client submits invalid state or monetary values. |Domain validation, stable errors, integer cents, transaction rollback, and immutable ledger records.
|T-003 |Repudiation |A user disputes a return, inspection, deduction, or issue. |Append-only audit entries with actor, timestamp, event, entity, and details; deposit entries reference the loan and trigger.
|T-004 |Information disclosure |A client requests member, loan, or deposit data through an interface. |Return only contract DTOs; enforce operation role policy; keep authentication as a deployment prerequisite outside release 1.
|T-005 |Denial of service |Repeated or oversized requests block counter operations. |Bound request sizes, validate identifiers and arrays, use indexed queries, and keep eligibility read-only.
|T-006 |Elevation of privilege |A member or clerk attempts technician operations. |Central application authorization policy applied before every use case; REST and CLI adapters cannot call persistence directly.
|===

=== 8.2 Security

Authorization is interface-level role authorization, not authentication. The application service receives a normalized role and checks the use-case permission matrix. `Workshop Technician` is required for inspection, maintenance, retirement, inspection listing, and reservation expiry; `Counter Clerk` is required for eligibility, issue, extension, return, and allocation; `Member` is required for member hold operations. All role checks are tested through both REST and CLI where available. Controls close T-001, T-002, T-004, and T-006.

=== 8.3 Test

The testing pyramid is:

* Domain unit tests for deposit rounding and bounds, eligibility predicates, state machines, queue order, suspension, maintenance thresholds, and invariants.
* Application service tests with an in-memory or transactional test repository for atomic success and rollback behavior.
* Contract tests for REST status codes, error shapes, JSON fields, roles, and CLI stdout/stderr/exit codes.
* A small number of end-to-end tests using the production persistence adapter and local process.

Tests trace to UC-01 through UC-07 and BR identifiers. Required invariants include non-negative deposit balance, deduction no greater than collected deposit, at most one active loan per item, at most one inspection report per loan, exactly one usage increment per completed loan, and stable hold ordering.

=== 8.4 Observability

The system must provide:

* Structured operation logs containing operation, actor role, outcome, stable error code, and correlation identifier.
* Metrics for operation latency, rejected issues by reason, inspection backlog, maintenance-due items, reservation expiry outcomes, and transaction failures.
* Audit entries as the domain record of state-changing actions, separate from diagnostic logs.
* Deposit ledger queries that reconstruct a loan balance from immutable transactions.

Logs must not replace the audit trail. Diagnostic retention and backup policy are operational decisions still open.

=== 8.5 Error Handling

Malformed input is rejected at the adapter boundary. Domain conflicts and validation failures are mapped to the status and stable error codes in the system interface specification. A failed state-changing operation rolls back all domain, audit, and deposit changes. Retried commands require idempotency semantics to be decided; until then, clients must not assume an unsafe retry is harmless. There is no external dependency requiring a circuit breaker or remote fallback.

=== 8.6 Persistence and Transactions

The persistence adapter must support transactions, uniqueness constraints, indexed lookup, and a durable append-only representation for deposit and audit records. A unit of work wraps every state-changing application service. The transaction includes domain state plus required audit and deposit entries. Read-only eligibility checks do not write.

=== 8.7 Time and Money

`Clock` is injected into application services. It supplies both current calendar date for overdue and expiry rules and UTC instants for audit and deposit timestamps. All monetary calculations use integer cents. The deposit policy is `ceil(replacementValueCents * 0.20)`, bounded to 500 through 10000 cents.

== 9. Architecture Decisions

=== ADR-001: Choose a modular monolith

Decision: implement one process with explicit modules and ports.

[cols="1,2,2,2"]
|===
|Criteria |Modular monolith |Microservices |Layered monolith without module rules

|Atomicity |+ One local transaction spans domain, audit, and deposit. |- Distributed transaction complexity. |+ Local transaction.
|Operational fit |+ One local process and no external services. |- Requires service deployment and operations. |+ One process.
|Boundary quality |+ Enforced module contracts and inward dependencies. |+ Strong process boundaries. |- Boundaries tend to erode.
|Change cost |+ Low for 400 items and 800 members. |- High coordination cost. |+ Low initially.
|===

The modular monolith wins because it preserves the required atomicity and operational simplicity while making the domain boundary testable.

=== ADR-002: Use an immutable deposit ledger

Decision: record collection, deduction, release, and retention as immutable transactions and derive balance from them.

[cols="1,2,2,2"]
|===
|Criteria |Immutable ledger |Mutable deposit balance |External payment ledger

|Traceability |+ Every transaction has timestamp, amount, type, trigger, and loan reference. |- Requires compensating history. |+ Potentially strong.
|Atomicity |+ Same local transaction as loan and inspection. |+ Simple local update. |- External consistency risk.
|Correctness |+ Recalculation detects drift; integer cents. |- Silent overwrite possible. |+ Specialist capability.
|Scope fit |+ No payment integration required. |+ Fits scope. |- Explicitly out of scope.
|===

=== ADR-003: Share domain services across REST and CLI

Decision: adapters map into common application commands; they do not implement use-case rules independently.

[cols="1,2,2,2"]
|===
|Criteria |Shared application services |Separate REST and CLI logic |Generate one interface from the other

|Cross-interface invariants |+ One rule path. |- Drift risk. |+ Possible but adds tooling.
|Testability |+ Service-level tests cover both adapters. |- Duplicate tests and behavior. |+ Depends on generator quality.
|Release-1 complexity |+ Small and direct. |+ Simple initially but costly later. |- Unnecessary constraint.
|===

=== ADR-004: Resolve reservation expiry explicitly

Decision: provide the specified expiry command and keep scheduling/lazy execution open.

[cols="1,2,2,2"]
|===
|Criteria |Explicit command |Embedded scheduler |Lazy resolution only

|Single-process fit |+ Works locally and visibly. |+ Possible but adds lifecycle behavior. |+ Minimal.
|Operational predictability |+ Operator can run and audit it. |+ Automatic but less visible. |- Depends on traffic.
|Contract certainty |+ Already specified by interface. |+ Not specified. |- Not specified.
|===

== 11. Risks and Technical Debt

=== 11.1 Risks

[cols="1,3,3,2"]
|===
|ID |Risk |Impact |Mitigation or decision

|R-001 |Release-1 role headers and CLI flags are not authenticated. |Unauthorized local or network caller could act as another role. |Document deployment trust boundary, reject missing/unsupported roles, and plan authentication as a separate capability. Related threat: T-001.
|R-002 |Concurrent issue, inspection, or allocation can create duplicate state without correct locking. |Incorrect availability, duplicate deposits, or duplicate reports. |Transactional write conflict handling, uniqueness constraints, and concurrency tests. Related threat: T-002.
|R-003 |Deposit ledger data loss or corruption prevents financial reconciliation. |Money traceability is lost. |Durable local persistence, backups, restore drills, and integrity checks. Backup policy remains open. Related threat: T-003.
|R-004 |Damage attribution across prior inspection reports is ambiguous. |Wrong loan may receive a deduction. |Keep prior inspection history available and resolve the domain rule before implementation. Related to UC-05 open question.
|R-005 |Reservation expiry processing is not automated. |Expired reservations may block allocation until a command runs. |Expose explicit expiry command; decide whether scheduling or lazy processing is needed. Related to ADR-004.
|===

=== 11.2 Technical Debt

* The persistence technology and schema migration tool are intentionally undecided.
* Idempotency keys for retried state-changing commands are still an open developer question.
* Backup, restoration, and data-directory conventions are still open operational questions.
* Authentication is outside release 1 and must not be mistaken for the role header contract.
* A future notification adapter may be added only outside the release-1 core and without changing domain invariants.

=== 11.3 ATAM Tradeoffs

The main sensitivity point is the transaction boundary: splitting audit, deposit, or domain state into separate services would directly threaten deposit correctness and traceability. A second sensitivity point is the shared eligibility policy: duplicate interface logic would threaten security. The principal tradeoff is operational simplicity versus automated reservation expiry; release 1 chooses explicit commands until operational needs are known.

== Open Questions and Handoff

The architecture is implementable within the stated release-1 constraints, but these questions remain intentionally open:

* Which persistence technology and migration approach are selected?
* Are duplicate holds for one member and category rejected or merged?
* What idempotency key is used for retried issue, return, inspection, maintenance, and reservation commands?
* How is prior damage selected when several historical inspection reports mention it?
* Are reservation expiry commands run manually, lazily, or by a local scheduler?
* What backup, restore, and local data-directory procedure is required?

These decisions must be resolved before the corresponding implementation slices are considered complete.
