= Socratic Code-Theory Recovery: Leihgut

Phase 1 of 2. This tree recovers the current theory of the bounded context from source code. It does not prescribe a future architecture. The bounded-context path used here is `src/leihgut/`; the repository is a modular monolith, so the boundaries below are inferred from responsibility and dependencies, not enforced as deployable services.

== Scope and reading rules

The recovered context is **Leihgut**, a local tool-lending system. `src/leihgut/` contains catalog, lending, inspection, deposit, training, reservation, maintenance, loss, audit, REST, SQLite, and clock concerns. `mitglied_id` is represented as text and member management is outside the code boundary: `src/leihgut/adapters/persistence/schema.sql` (comments before `einweisung`).

An `[ANSWERED]` leaf is grounded in one or more exact source anchors. An `[OPEN]` leaf records a question that code alone cannot settle. The latter is intentionally not converted into a design assumption.

== Q1 What problem does this bounded context solve, and for whom?

=== Q1.1 Product identity

==== Q1.1.a What product is implemented?

[ANSWERED]

The product is a "Bibliothek der Dinge" for lending tools and equipment. The README identifies approximately 400 items and 800 members and names lending, deposits, maintenance, and reservations as the problem domain: `README.adoc` ("Worum es geht").

==== Q1.1.b What distinguishes this domain from ordinary lending?

[ANSWERED]

Items have a lifecycle with maintenance and write-off states; a deposit is collateral; and training is attached to a member and category. The item states are encoded by `GegenstandZustand` in `src/leihgut/domain/gegenstand.py::GegenstandZustand`; the domain distinctions are stated in `README.adoc` ("Warum das mehr ist als eine Bücherei").

=== Q1.2 Primary users

==== Q1.2.a Who operates the system?

[ANSWERED]

The README names Karim, the counter worker; Sabine, the member; and Rolf, the workshop worker: `README.adoc` ("Personas"). REST role checks are implemented by `src/leihgut/adapters/rest/rollen.py::erfordere_rolle`.

==== Q1.2.b Which actor performs which work?

[ANSWERED]

Counter work is checkout and return (`src/leihgut/anwendungskern/ausleihe_service.py::gegenstand_ausgeben`, `::gegenstand_zuruecknehmen`). Member-facing work includes availability and reservation (`src/leihgut/anwendungskern/verfuegbarkeit_service.py::verfuegbarkeit_pruefen`, `src/leihgut/anwendungskern/vormerkung_service.py::vormerkung_erfassen`). Workshop work includes inspection, maintenance, training, and loss (`src/leihgut/anwendungskern/pruefung_service.py::pruefung_abschliessen`, `wartung_service.py::wartung_abschliessen`, `einweisung_service.py::einweisung_erfassen`, `verlust_service.py::verlust_erfassen`).

=== Q1.3 Channels

==== Q1.3.a Which channels cross the system boundary?

[ANSWERED]

The README specifies a REST API and a CLI for workshop tasks, with no web UI: `README.adoc` ("Rahmenbedingungen"). The implemented HTTP adapter is `src/leihgut/adapters/rest/app.py`; role information enters through the `X-Rolle` header in `src/leihgut/adapters/rest/rollen.py::erfordere_rolle`.

==== Q1.3.b Is identity/authentication part of this context?

[ANSWERED]

No real login is implemented or required by the stated boundary. The README says roles are supplied by a header or CLI flag and are not checked as authentication: `README.adoc` ("Rahmenbedingungen").

=== Q1.4 Why it was built

==== Q1.4.a Which failures is the system intended to prevent?

[ANSWERED]

The README identifies wrong deposit refunds, lending maintenance-due items, and reservation violations caused by extensions: `README.adoc` ("Worum es geht"). The implementation addresses these through deposit calculation (`src/leihgut/domain/kaution.py::kaution_berechnen`), item-state validation (`src/leihgut/anwendungskern/ausleihe_service.py::_ausgabe_pruefen`), and extension validation (`src/leihgut/anwendungskern/verlaengerung_service.py::_verlaengerung_validieren`).

The imported exception classes and endpoint handlers define domain errors such as unavailable item, duplicate reservation, overdue loan, missing training, and excessive deposit deduction.

=== Q2.4 Data/entity model

==== Q2.4.a What are the core entities and values?

[ANSWERED]

The domain modules define `Gegenstand`, `Ausleihe`, `Kategorie`, `Kaution`, `Kautionsbewegung`, `Einweisung`, `Vormerkung`, `Pruefprotokoll`, `MaengelEintrag`, and `AuditLogEintrag`: `src/leihgut/domain/`. Their persistence relationships and constraints are defined in `src/leihgut/adapters/persistence/schema.sql`.

==== Q2.4.b What lifecycle invariants control lending?

[ANSWERED]

`GegenstandZustand` models available, loaned, inspection, maintenance-due, reserved, and written-off states: `src/leihgut/domain/gegenstand.py::GegenstandZustand`. `AusleiheZustand` models active, returned, completed, and lost completion states: `src/leihgut/domain/ausleihe.py::AusleiheZustand`; overdue means active and past the return deadline in `Ausleihe::ist_ueberfaellig`.

==== Q2.4.c Which persistence invariants are enforced below the application layer?

[ANSWERED]

`schema.sql` enforces one active loan per item with `ux_ausleihe_aktiv_je_gegenstand`, one valid training per member/category with `ux_einweisung_gueltig_je_mitglied_kategorie`, one open reservation per member/category with `ux_vormerkung_offen_je_mitglied_kategorie`, positive values with CHECK constraints, and audit immutability with UPDATE/DELETE triggers.

=== Q2.6 Cross-cutting business rules

==== Q2.6.a Which rules are explicit in code?

[ANSWERED]

Checkout requires an available item, permits at most three active loans per member, and rejects blocked members or missing training: `src/leihgut/anwendungskern/ausleihe_service.py::_ausgabe_pruefen`. Extension rejects overdue/already-extended loans: `verlaengerung_service.py::_verlaengerung_validieren`. Deposit is 20% of replacement value, bounded by 5 and 100 euros: `src/leihgut/domain/kaution.py::kaution_berechnen`. FIFO reservation order is calculated by `vormerkung_service.py::_reihenfolge_berechnen`; inspection and maintenance determine/reset item state and usage count in `pruefung_service.py` and `wartung_service.py`.

== Q3 What is the architecture of this bounded context?

=== Q3.1 Introduction and Goals

[ANSWERED]

The stated goal is a local system that prevents lending, deposit, maintenance, and reservation errors: `README.adoc` ("Worum es geht"). The implementation is a Python package under `src/leihgut/`, exercised by the test suite under `tests/`.

=== Q3.2 Constraints

[ANSWERED]

The system is a single locally startable process, uses REST plus a workshop CLI boundary, has no external services, does not implement real login, and uses an exchangeable date source: `README.adoc` ("Rahmenbedingungen"). Python/dependency constraints are declared in `pyproject.toml`.

=== Q3.3 Context and Scope

[ANSWERED]

The bounded context contains catalog, lending, inspection, training, reservations, maintenance, loss, deposits, and audit concerns. Member management, email, and payment systems are outside the source boundary; only `mitglied_id` and a blocked flag are carried in lending-related data, as documented by comments in `src/leihgut/adapters/persistence/schema.sql`.

==== Q3.3.a What are the inferred internal context boundaries?

[ANSWERED]

Catalog (`Kategorie`, `Gegenstand`), lending (`Ausleihe`), training (`Einweisung`), reservation (`Vormerkung`), inspection/defects (`Pruefprotokoll`, `MaengelEintrag`), maintenance, loss, and deposit movements are capability boundaries inside one bounded context. They communicate through application-service calls and repository ports; `src/leihgut/anwendungskern/ausleihe_service.py::gegenstand_zuruecknehmen` calls reservation management after return.

=== Q3.4 Solution Strategy

[ANSWERED]

The solution uses a hexagonal/modular structure: domain models in `src/leihgut/domain/`, application services in `src/leihgut/anwendungskern/`, Protocol ports in `src/leihgut/ports/`, REST/system-clock adapters in `src/leihgut/adapters/`, and SQLite persistence adapters in `src/leihgut/adapters/persistence/`. The REST module docstring in `src/leihgut/adapters/rest/app.py` explicitly says the adapter contains no domain logic.

=== Q3.5 Building Block View

[ANSWERED]

The primary building blocks are domain dataclasses/enums, application services, repository/clock Protocols, REST adapters, SQLite repositories, and the SQLite schema. `src/leihgut/adapters/rest/app.py::create_app` wires concrete repositories and the clock into the service layer; the `src/leihgut/ports/` modules define the inward-facing interfaces.

=== Q3.6 Runtime View

[ANSWERED]

A request enters a REST endpoint, passes `erfordere_rolle`, is converted from a Pydantic request schema, calls an application service, reads/writes through injected repositories, and is mapped to JSON/HTTP status. Checkout orchestration is visible in `src/leihgut/anwendungskern/ausleihe_service.py::gegenstand_ausgeben`; the repository transaction and concurrent-check behavior are visible in `src/leihgut/adapters/persistence/sqlite_ausleihe_repository.py`.

=== Q3.8 Crosscutting Concepts

==== Q3.8.a How are security and authorization handled?

[ANSWERED]

Role checking is centralized at the REST boundary by `src/leihgut/adapters/rest/rollen.py::erfordere_rolle` and occurs before service invocation in `src/leihgut/adapters/rest/app.py`. The README explicitly states that the header/CLI role is not authenticated.

==== Q3.8.b How are consistency and concurrency handled?

[ANSWERED]

The schema has a partial unique index allowing at most one active loan per item: `src/leihgut/adapters/persistence/schema.sql::ux_ausleihe_aktiv_je_gegenstand`. The SQLite loan repository uses an explicit transaction/check-then-act path in `src/leihgut/adapters/persistence/sqlite_ausleihe_repository.py`.

==== Q3.8.c How are audit and observability handled?

[ANSWERED]

`AuditLogEintrag` is append-only in `src/leihgut/domain/audit_log.py`; SQLite triggers reject UPDATE and DELETE in `schema.sql`. Statistics are calculated by `src/leihgut/anwendungskern/audit_retention_service.py::get_audit_log_stats` and exposed by the admin REST endpoint in `app.py`.

==== Q3.8.d How are errors and recovery handled?

[ANSWERED]

Application services return domain-specific error results/exceptions, and REST maps them to HTTP responses in `src/leihgut/adapters/rest/app.py`. SQLite repository operations use transaction commit/rollback behavior; no external-service retry or circuit breaker is present because the README states there are no external services.

== Q4 What quality goals drive the design?

The following are derived quality scenarios only from observable code behavior. They do not invent target values. Q4.9 is the only quality-goal ranking leaf and is open.

=== Q4.1 Functional suitability

[ANSWERED]

Scenario: When a checkout, return, inspection, reservation, training, maintenance, or loss operation receives invalid state or values, the application service rejects it with a domain-specific result/error. Evidence: `src/leihgut/anwendungskern/ausleihe_service.py::_ausgabe_pruefen`, `pruefung_service.py::_pruefung_pruefen`, `katalog_service.py::_kategorie_werte_pruefen`, and the service-specific tests under `tests/`.

=== Q4.2 Performance efficiency

[ANSWERED]

Scenario: A normal operation runs synchronously in one local process and accesses SQLite through repository methods; no cache, asynchronous worker, or retry path is encoded. Evidence: service orchestration in `src/leihgut/anwendungskern/` and concrete SQL adapters in `src/leihgut/adapters/persistence/`. The code supplies no latency or throughput target.

=== Q4.3 Compatibility

[ANSWERED]

Scenario: The application core depends on repository and clock Protocols, while SQLite and system time are adapters. Replacing those implementations can preserve the application-service contracts if the Protocols remain satisfied. Evidence: `src/leihgut/ports/` and `src/leihgut/adapters/rest/app.py::create_app`.

=== Q4.4 Usability

[ANSWERED]

Scenario: A consumer receives structured HTTP status/error responses rather than application exceptions directly, and availability is exposed as a read-only query. Evidence: `src/leihgut/adapters/rest/app.py` error mappings and `src/leihgut/anwendungskern/verfuegbarkeit_service.py::verfuegbarkeit_pruefen`. The code does not define human workflow or response-time targets.

=== Q4.5 Reliability

[ANSWERED]

Scenario: Concurrent attempts to create two active loans for one item are constrained by `ux_ausleihe_aktiv_je_gegenstand`, while the repository uses an explicit transaction path. Evidence: `src/leihgut/adapters/persistence/schema.sql::ux_ausleihe_aktiv_je_gegenstand` and `src/leihgut/adapters/persistence/sqlite_ausleihe_repository.py`.

=== Q4.6 Security

[ANSWERED]

Scenario: An endpoint with an unacceptable declared role is rejected before its application service is called. Evidence: `src/leihgut/adapters/rest/rollen.py::erfordere_rolle` and the guarded endpoint definitions in `src/leihgut/adapters/rest/app.py`. The code also explicitly leaves authentication and cryptographic role proof out of scope in `README.adoc`.

=== Q4.7 Maintainability

[ANSWERED]

Scenario: Domain rules can be exercised without infrastructure through pure domain functions and application-service validation functions; infrastructure is substituted through Protocol ports. Evidence: `src/leihgut/domain/kaution.py::kaution_berechnen`, validation functions under `src/leihgut/anwendungskern/`, and `src/leihgut/ports/`.

=== Q4.8 Portability

[ANSWERED]

Scenario: The application core can be wired with a different repository or clock implementation without changing the Protocol consumers. Evidence: `src/leihgut/ports/clock.py`, repository Protocols under `src/leihgut/ports/`, and dependency injection in `src/leihgut/adapters/rest/app.py::create_app`. The current deployment remains specifically Python plus SQLite.
